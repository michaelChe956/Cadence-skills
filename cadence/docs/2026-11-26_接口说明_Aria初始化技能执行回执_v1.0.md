# Aria 对接初始化技能执行回执 v1

`cadence.skill-receipt/v1` 由实际执行的技能脚本写到 stdout。Aria 要确认一次规则配置已应用，应在本次工具调用的输出中匹配 `skill=rule-config`、`action=apply`、本次 `run_id`、`exit_code=0` 和 `overall=success`。成功的预演也会返回 `success / 0`，其 `action` 为 `dry-run`。

## 从哪里读取回执

按调度时预期的技能选择解析方式，输入取自 provider 返回的本次脚本 stdout。一个 turn 中先预演再应用时，分别保存两次调用的 stdout 和运行 ID。stderr 单独保留作诊断。

| 预期 `skill` | `action` 的有效值 | stdout 的读取方式 | 业务明细 |
|---|---|---|---|
| [pre-check](../../cadence-init/skills/pre-check/SKILL.md) | `run`、`check` | 将整个 stdout 解析为一个 JSON 对象 | `steps`、`phases`、`warnings`、`backups`。各阶段的 `action` 位于 `phases` 中 |
| [rule-config](../../cadence-init/skills/rule-config/SKILL.md) | `dry-run`、`apply`、`verify`、`remove-permission-gate` | 解析最后一个非空行的单行 JSON | `native`、`report`、`failure`。`--verify` 对应 `verify`，`--remove-permission-gate` 对应 `remove-permission-gate` |
| [mcp-configuration](../../cadence-init/skills/mcp-configuration/SKILL.md) | `apply` | 解析最后一个非空行的单行 JSON | `native`、`report`、`pending`、`failure` |
| [project-rules-examples](../../cadence-init/skills/project-rules-examples/SKILL.md) | `apply` | 解析最后一个非空行的单行 JSON。`apply.sh` 转交 `apply.py`，只产生一份回执 | `counts`、`completed`、`needs_rule_config`、`pending`、`failure` |

三个单行回执都保留 `overall` 为末键。JSON 解码能还原中文、引号和换行等转义字符。`--help` 只显示帮助。`rule-config verify --json` 返回单份原生自检 JSON，按自检协议读取 `mode`、`checks` 和 `exit_code`。需要 v1 回执的自检调用使用 `verify`。

## 关联和判定一次调用

1. **分配运行 ID。** 在启动脚本前记录预期的 `skill`、`action` 和本次 ID，通过子进程环境变量 `CADENCE_SKILL_RUN_ID` 传入。预演、应用和重试可各用一个 ID。`run_id` 原样回传字符串，显式空串仍是 `""`，用户独立运行时未设置则为 JSON `null`。
2. **校验身份。** 确认 `schema` 严格等于 `cadence.skill-receipt/v1`，`skill`、顶层 `action` 和 `run_id` 都与本次期望匹配。缺回执、JSON 无法解析、版本或身份不符时，将本次预期动作记为“未确认”。参数错误使动作无法确定时，脚本会给出 `action: null` 和失败结果，保留该诊断。
3. **读取结果。** `exit_code` 是进程的整数退出码。provider 若同时提供了进程返回码，两者应一致。`overall=success` 且 `exit_code=0` 表示该动作成功，包括已配置项目再次 `apply` 时的零文件变更。`overall=failed` 或非零退出码表示失败，记录 `failure`、已有明细和 stderr。`pre-check` 普通模式的 `partial / 0` 表示部分完成，需要检查失败阶段。MCP 的 `native=degraded` 可以与 `success / 0` 同时出现，`pending` 给出待人工处理项数。

预检在执行期间收到 HUP、INT 或 TERM 会输出 `overall=failed`，对应退出码为 129、130 或 143。

`rule-config` 的 `--report` 和 `--decisions` 应放在项目根外。回执的 `report` 给出本次请求的路径，即使该路径未通过校验。MCP 配置已合并后，单独的报告写入失败也会返回 `failed / 1`，已完成的合并会保留。

## 联调样例

在 Cadence-skills 仓库根目录运行以下命令。它们对同一个临时项目先预演再应用，用两种 Python 调用方式得到相同格式的回执。

```bash
(
  set -e
  aria_demo=$(mktemp -d)
  trap 'rm -rf -- "$aria_demo"' EXIT
  mkdir "$aria_demo/project"
  script="$PWD/cadence-init/skills/rule-config/scripts/rule-config.py"
  CADENCE_SKILL_RUN_ID=demo-preview python3 "$script" dry-run \
    --project-root "$aria_demo/project" --report "$aria_demo/preview.json"
  CADENCE_SKILL_RUN_ID=demo-apply python3 -B "$script" apply \
    --project-root "$aria_demo/project" --report "$aria_demo/apply.json"
)
```

以下完整回执将临时根写为 `/tmp/aria`，以 JSON 解码后的中文展示。

**已配置项目再次应用**。进程退出 0，项目文件零变更。

```json
{"schema":"cadence.skill-receipt/v1","skill":"rule-config","action":"apply","exit_code":0,"native":"ok","report":"/tmp/aria/report.json","failure":null,"run_id":"run-41","overall":"success"}
```

**已识别 `apply`，报告路径位于项目根内**。进程退出 2，脚本拒绝写入该报告。

```json
{"schema":"cadence.skill-receipt/v1","skill":"rule-config","action":"apply","exit_code":2,"native":null,"report":"/tmp/aria/project/report.json","failure":{"file":"/tmp/aria/project/report.json","reason":"路径 /tmp/aria/project/report.json 位于项目根 /tmp/aria/project 之内（外部输入必须位于根外）","recovery":"将 --report 路径放在项目根目录之外"},"run_id":"run-42","overall":"failed"}
```

## 接入位置与上线检查

Aria `3d0775e0` 在 `src/product/logical_codebase/coordinator_provider_turn.inc.rs` 的 `ProviderEvent::ToolResult` 分支消费工具结果，`coordinator_turn_output.inc.rs` 的 `recipe_report_verdict` 从原文扫描 `overall`。在这个入口按预期动作解析 v1 并关联 `run_id`，即可区分上面的预演和应用。保留原始工具结果有助于诊断缺回执、输出截断或路径校验失败。

部署后，从 provider 实际发现技能的安装目录执行一次 `rule-config dry-run`。给它指定新的运行 ID 和根外报告路径，在工具结果中核对 `schema`、`action=dry-run` 和该 ID。随后用另一个 ID 执行 `apply`，核对 `action=apply` 和第二个 ID。这样可以同时验证安装副本、环境变量传递和 Aria 的结果匹配。
