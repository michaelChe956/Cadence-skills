# 初始化项目工作流验收记录

## 生成与升级

测试使用 `rule-config.py` 的普通 `dry-run`、`apply`、`verify` 入口和 OpenSpec 2.1.1。空项目生成双入口 v6、完整协作规则 v2 和四组 artifact 规则。`verify` 为 `healthy`。

用修改前的 `rule-config` 实际生成 v5 项目，再运行新版。dry-run 全项目快照相同。首次 apply 备份 `CLAUDE.md`、`AGENTS.md`、协作规则和 `openspec/config.yaml`。再次 apply 新增备份 0、差异文件 0，比较包括文件内容、修改时间与软链目标。五份历史 v1 完整正文分别混入项目条款和独立覆盖，五组均通过保留与二次零写入检查。

`cadence-init/skills/rule-config/tests/test_workflow_upgrade.py` 从临时项目运行真实 CLI，覆盖同文出现在其他 artifact、旧句带用户后缀、前导空白、无本地基线、开启的提交开关和入口围栏。完整生命周期脚本另覆盖 v0 入口升级及备份失败关闭，原生 Bash 运行结果为 `SUMMARY pass=103 fail=0`。rule-config 的单测与真实子进程用例合计 358 项通过。stage1 断言 20 项通过，轨迹、探针和 Docker 评分单测 40 项通过。

## 恢复会话

在初始化后的隔离项目中使用 `omp -p --session-dir` 保存用户委托，后续在同目录启动新的 `omp --continue` 进程。场景使用导出公开目录的任务 `export-index`，Plan 步骤 P1 回指工作包 1.1 与 R1/S1。客户端模型为 `my-openai/gpt-6.2-sol`。探针让客户端只交接当前下一步。审查通过状态作为测试输入，观测项为送审对象、实际人工询问和下一阶段。本次仓库变更的 Design 双审、联合包双审另由真实审查任务完成。

| 输入 | 实际观察 |
|---|---|
| 默认委托实施 | 单独送完整 Design，双审通过后询问 Design 一次。change 与 Plan 同版送审一次，通过后执行 P1。 |
| 明确免确认 | 单独送 Design 一次，再联合送 change 与 Plan 一次，人工询问为零。 |
| 明确看 Plan | 只有 Design 的现场在 Design 双审通过后询问 Design。收到确认才进入联合编写。同版联合包送审时无需回复，通过后询问 Plan 一次，确认后恢复到 P1。 |
| Design 已确认但只有 change | 恢复到 `writing-plans` 补 Plan 和引用，再严格校验并联合送审。 |
| change 严格校验失败 | 实际 `openspec validate export-index --strict` 退出 1。客户端要求修订规格并重跑，实施保持阻塞。 |
| 漏了工作包到 Plan 的反向引用 | 严格校验退出 0。客户端仍要求补 1.1 → P1，再校验与联合送审。 |
| 已审 Plan v1 被 v2 替换 | 沿用 Design 的通过记录，要求对当前 change 与 Plan v2 再校验、核对映射和联合双审。 |
| 实施中改变 Design 验收范围 | 停止实施并返回 Design，按新版恢复审查与确认。 |
| 只委托出方案 | 当前版双审通过后交付 Design、change、Plan。 |

原生 `openspec instructions apply --change export-index --json` 在仅缺外部 Plan 时仍返回 `ready`。生成的 context 包含项目门禁。可用 `openspec instructions tasks --change export-index --json` 查看进入工作包指令的双向引用要求。
