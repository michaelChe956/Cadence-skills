# 初始化项目的 Design、change 与 Plan 工作流

本次调整面向运行 `rule-config` 的项目。用户已经确定阶段顺序、人工确认策略与验收行为，并委托实施。本文记录生成和升级这些规则的设计，供实施前审阅。

## 生成后的任务流程

1. 命中 OpenSpec 阈值时，先用 `brainstorming` 确定范围、架构、验收边界，将完整 Design 写入 `cadence/designs/`。只送审这一版 Design。双审均通过后，默认等用户确认。用户已经对该版 Design 表达“Design 没问题，继续”时，记录并沿用。
2. Design 通过双审且人工确认已满足或被明确免除，进入联合编写。先在 change 中形成可引用的 requirement、scenario 和编号工作包，随即用 `writing-plans` 在 `cadence/plans/` 展开对应的文件、接口、顺序与验证。两份草稿在 Design 范围内可以互相校正。工作包引用相关场景和 Plan 步骤，Plan 步骤回指 change、工作包和场景。
3. 两份产物齐全、`openspec validate <change-id> --strict` 通过、双向映射完整，才将当前版 change 与 Plan 作为一个包双审。两项审查都针对同一版。通过后按委托自动进入实施或交付文档。显式要求看 Plan 时，在联合双审后等一次确认。修订送审内容时，以修订后的版本参加相应审查。
4. 人工确认决定与委托范围属于本任务。明确“这次不用确认，直接继续”免除剩余人工确认，两个双审仍保留。显式要求在 Plan 完成后查看，在联合双审后设一次等待。恢复时从已有 Design、change、Plan 或交接记录读取本任务委托、最近的显式决定、产物版本及审查结果。已满足的确认直接沿用，仍在等待的确认只消费一次。缺 Plan 回联合编写补 Plan，严格校验失败回修 change，再校验。缺当前版审查证据则回对应送审阶段。实施中改变 Design 边界时回到 Design 阶段。

项目门禁优先于 `brainstorming`、`writing-plans` 及 OpenSpec 默认交接提示。已委托实施的任务在满足联合门禁后直接按 Plan 执行。仅当用户另设 Plan 确认点时才等待该确认。

## 生成与迁移

沿用 `rule-config` 的发布路径。双入口的 L0 保留最短的阶段路标，L1 给出完整送审与恢复条件，OpenSpec 的 context 和各 artifact 规则写明产物职责与引用方式。审查执行、代理选角、派工与复核方式由 `cadence-subagents-config` 管理。复用任务产物或交接记载决定，无需新增运行时服务或 Hook。

L0 把前一版本纳入历史模板，升级时仅把块内未知用户行迁出保留。L1 优先使用记录的框架基线，在无基线但可识别旧版时用历史模板区分旧框架正文和用户改写，沿用原有 overlay 与备份策略。OpenSpec 对可解析配置限定迁移位置，按 context 完整逻辑行、按照属 artifact 匹配的完整旧规则项识别退役条款。带前后缀、仅含相同关键词或其他位置的用户文本保留，其他配置和提交开关按现行合并策略处理。

历史识别覆盖已发布的 L0 v1–v5 和此前支持的 v0，以及 L1 同名 v1 的早期长正文、简版、带 frontmatter 版。优先取 manifest 基线。无基线时只认历史框架完整原文或能归属于旧正常模板的完整行，无法归属的内容保留并按现有覆盖机制提示。独立用户 overlay 原文保留。

单改模板会使旧 context 继续生效。整份覆盖 YAML 会丢失用户 context、规则和扩展字段。因此选择在原有保守合并器内迁移已发布的框架条款，并让 dry-run 与 apply 使用同一候选。仓内生效的入口、规则、配置和规格与生成源同步。

## 验收

- 用正常 `rule-config` 的 dry-run、apply、verify 检查新项目和旧版项目。旧项目混入用户 context、artifact 规则、入口自定义行和覆盖规则，使用非默认提交开关。有无本地框架基线均覆盖。比较二次 apply 前后的文件内容、写入和备份。
- 从生成的入口恢复默认、免确认、自定义 Plan 确认及已确认 Design 的任务。按人工询问、独立 Design 双审、联合双审和交付去向核对，含只出方案与实施两类委托。
- 对仅有 change、校验失败和工作包追溯不全的任务，确认恢复后先补对应产物，验证及联合双审就绪后才允许实施。使用真正的 OpenSpec 严格校验，区分产物静态检查和实际会话观察。
