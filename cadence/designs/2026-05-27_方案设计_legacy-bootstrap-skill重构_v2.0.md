# Legacy-Bootstrap Skill 重构设计

> 版本：v2.0 | 日期：2026-05-27 | 状态：已确认

## 1. 问题陈述

当前 `legacy-bootstrap` skill 存在两个核心问题：

1. **执行不合规** — SOP 定义了 8 种标准产物，但实际执行时将所有内容塞进 1-2 个文件，未按清单逐一生成
2. **产物类型不够** — 缺少 API 文档、服务依赖关系、组件文档等项目类型相关的专属产物

## 2. 设计目标

- 将松散的"分析后批量输出"改为**类型驱动的产物管线**
- 按项目类型条件触发专属产物，确保覆盖完整
- 逐产物生成并报告，杜绝静默遗漏
- 产物详细程度达到端点清单级别（API 文档为例）

## 3. 整体流程架构

```
Phase 1: 环境检测
  ├─ 确认项目根目录
  ├─ 读取项目规则（CLAUDE.md / AGENTS.md）
  └─ 运行 repomix 生成快照

Phase 2: 项目类型识别
  ├─ 从 repomix 输出中提取信号（框架、依赖、目录结构）
  ├─ 判定项目类型（可多选，取并集）
  └─ 确定产物清单 = 核心产物 + 类型专属产物

Phase 3: 逐产物生成管线
  ├─ 按清单顺序，逐个产物：
  │   ├─ 从 repomix 提取相关信息
  │   ├─ 写入 cadence/ 对应路径
  │   └─ 输出确认行："✓ 已生成: <路径>"
  └─ 若某产物证据不足 → 输出："⚠ 跳过: <产物名> — 原因: <说明>"

Phase 4: 收尾验证 + 报告
  ├─ 检查所有应生成文件是否存在于磁盘
  ├─ 更新 CLAUDE.md / AGENTS.md 认知链接
  └─ 输出 Bootstrap 汇总表
```

### 关键设计决策

- Phase 2 支持**组合类型**（如"后端单体 + 前端应用"），产物清单取并集
- Phase 3 串行执行，每个产物独立完成后才进入下一个
- 跳过产物必须给出原因，不允许静默跳过

## 4. 项目类型识别规则

### 类型检测信号

| 项目类型 | 检测信号 |
|---------|---------|
| **前端应用** | `package.json` 含 react/vue/angular/svelte 依赖；存在 `src/components/`、`src/pages/`、`app/` 等目录；有 vite/webpack/next 配置 |
| **后端服务（单体）** | `Cargo.toml`/`go.mod`/`pom.xml`/`package.json` 含 express/fastify/nest；存在 `src/routes/`、`src/handlers/`、`controllers/`；有数据库依赖 |
| **后端服务（微服务）** | 多个独立服务目录各有自己的入口/配置；存在 docker-compose 多服务定义；有 API 网关/服务注册/消息队列依赖 |
| **全栈应用** | 同时满足前端 + 后端信号；或使用 Next.js/Nuxt/Remix 等全栈框架 |
| **CLI/工具库** | `bin/` 目录；`package.json` 有 `bin` 字段；`Cargo.toml` 有 `[[bin]]`；存在 `commands/`、`cli/` 目录 |
| **基础设施/DevOps** | 存在 `.tf` 文件、`k8s/`、`helm/`、`Dockerfile`、`ansible/`、`pulumi/` |

### 组合规则

- 一个项目可匹配多个类型，产物清单取并集
- 若无法识别类型 → 回退为"未知类型"，只生成核心产物，并在报告中标注

### 用户确认

类型识别完成后，向用户展示判定结果并请求确认。用户可修正类型判定，修正后重新计算产物清单。

## 6. 执行保障机制

### 逐产物生成协议

每个产物遵循固定三步：

1. **提取** — 从 repomix 输出中定位相关代码/配置片段
2. **写入** — 生成文档并写入 cadence/ 对应路径
3. **确认** — 输出一行状态报告

状态报告格式：

```
✓ [1/15] 已生成: cadence/architecture/2026-05-27_架构文档_系统总览_v1.0.md
✓ [2/15] 已生成: cadence/architecture/2026-05-27_架构文档_模块地图_v1.0.md
⚠ [3/15] 跳过: 数据模型 — 原因: 项目无持久化层，纯内存计算
```

### 收尾验证

1. 遍历产物清单，检查每个"已生成"文件是否真实存在
2. 检查文件非空（> 100 字符）
3. 若发现缺失/空文件 → 重新生成该产物
4. 验证通过后输出汇总表

### 禁止行为

- ❌ 禁止将多个产物合并到一个文件中
- ❌ 禁止静默跳过产物（必须报告原因）
- ❌ 禁止生成空文件或只有标题的文件
- ❌ 禁止在产物中编造无证据支撑的内容（用 `[UNKNOWN]` 标记）

## 7. 深度模式

### 标准模式 vs 深度模式

| 维度 | 标准模式 | 深度模式 |
|------|---------|---------|
| 核心产物 | 全部生成 | 全部生成 |
| 类型专属产物 | 全部生成 | 全部生成 |
| 粒度 | 系统级 | 模块级（每个核心模块单独一份） |
| 额外产物 | 无 | 每模块：模块分析 + 风险分析 + 领域模型 |
| 适用场景 | 中小项目、快速了解 | 大型项目（>50 文件）、深入改造 |

### 深度模式额外产物

对每个核心模块生成：

```
cadence/architecture/..._架构文档_<模块名>模块分析_v1.0.md
cadence/analysis-docs/..._分析报告_<模块名>风险分析_v1.0.md
cadence/models/..._数据模型_<模块名>领域模型_v1.0.md
```

### 模式选择

- 默认询问用户选择模式
- 若 repomix 输出 > 200,000 tokens 或文件数 > 100，建议深度模式
- 用户可指定 `--deep` 或 `--standard`

## 8. CLAUDE.md / AGENTS.md 更新

生成产物后，更新入口文档的认知链接区域：

- 只链接实际生成的文档（不链接跳过的）
- 按"首选入口 → 修改前必读 → 类型专属"分层组织
- 使用相对路径

## 9. 与现有 SOP 的差异

| 维度 | 旧 SOP | 新设计 |
|------|--------|--------|
| 产物生成方式 | 分析完毕后批量输出 | 逐个生成，边做边报告 |
| 产物类型 | 固定 8 种 | 核心 8 + 类型专属最多 13 |
| 项目类型感知 | 无 | 6 种类型，组合检测 |
| 执行保障 | 无 | 逐产物确认 + 收尾验证 |
| 深度模式 | 有定义但模糊 | 明确为模块级拆分 |
