# 方案设计：HTTP MCP 五端兼容性观测体系（宿主交互车道）v1.0

> 生成时间：2026-09-11
> 状态：设计已与用户确认方向（ter 主线 + oracle 忠实度标准合并方案）；待本文档评审后进 OpenSpec
> 研究参与：主会话（glm-5.3）+ oracle（测量有效性归因）+ ter-task（五端挂载机制与工程落地）
> 前史：M 组探针四轮容器实测踩坑全记录见本文「一、背景」

## 一、背景：要测什么、为什么现有方式错了

**目标**：用户在自己机器的项目目录里对 claude/codex/pi/kimi/omp 说「用 web-search-prime 搜一下」——三个 bigmodel HTTP MCP（web-search-prime / web-reader / zread）能用/不能用，五端矩阵进透视表。

**基准事实（用户本机交互式实测）**：仅 codex 挂（rmcp streamable-http × bigmodel 网关：initialize 响应后关流报 `Transport channel closed`；真实 key curl 全序列 200 证明端点健康）；其余四端可用。

**四轮容器实测为何全错（oracle 分层归因）**：三层保真度同时被替换，测出的是 harness 伪影不是产品——

| 层 | 替换内容 | 伪影表现 |
|---|---|---|
| L1 配置源 | 合成项目配置（mcp-configuration 占位 key + `_preset_mcp_real_keys` 真化）≠ 用户全局配置 | 占位 key 致启动即鉴权失败；codex 容器报 Deserialize 错误体 ≠ 宿主 channel closed |
| L2 环境 | 容器最小 HOME ≠ 宿主完整配置生态 | claude 缺 `~/.claude.json` 项目批准态；挂载行为与宿主不一致 |
| L3 交互 | headless `-p` ≠ 交互式 | 挂载/授权路径差异未校准 |
| L4 测量 | 评分口径 | 已修（见「三、既有资产」） |

**结论**：继续给合成配置打补丁 = 测 harness 自身。「模拟用户方式」的唯一忠实路径 = 在用户真实环境用交互式会话测。

## 二、五端 MCP 挂载机制事实表（ter-task 实测/考证）

| 端 | 用户侧挂载路径 | 授权/信任 | http 类型 |
|---|---|---|---|
| claude | 项目 `.mcp.json` 自动发现；`~/.claude` 凭据；`~/.claude.json` 存项目批准 | 首次项目 MCP 需批准（一次性人工） | 支持（宿主 headless 实测亦挂载） |
| codex | 项目 `.mcp.json` / `.codex/config.toml`（url+http_headers） | 无授权概念 | 支持（客户端×网关兼容性问题本体） |
| pi | pi-mcp-adapter 读项目 `.mcp.json`；`~/.pi/agent` 扩展/信任 | 保留真实信任态 | 项目级 http 挂载行为以实测为准 |
| kimi | `~/.kimi-code/mcp.json` → 项目 `.mcp.json` → cwd 三层覆盖 | 原生 http | 支持 |
| omp | `~/.omp/agent/{models,config}.yml`（宿主实测三 MCP 可用） | — | 支持 |

## 三、方案：宿主交互车道（ter 主线）+ 忠实度四维（oracle 标准）

### 3.1 车道设计

- **新增 `run_user_mcp_probe` 入口**：不走 docker、不走 `_preset_mcp_real_keys`/`_rebuild_codex_toml`（这些仅保留给安装回归用途）；`night.py` 仅做 M 组路由分流
- 执行形态：真实 HOME、用户项目 cwd、**五端并行 PTY 交互会话**（禁用 `-p` headless）
- 每端流程：①启动会话先发「列出当前可用的 MCP 工具名」固化挂载清单 → ②依次输入 M1-M3 探针原话 → ③存原生 transcript（复用现有五端 adapter 解析，omp 复用 pi）
- **首轮一次性人工点**：claude 项目 MCP 批准（用户已批准过的项目可免）

### 3.2 忠实度四维验收标准（oracle）

1. **配置**：用户真实配置零改写（与宿主 diff 为零）；禁合成/预置任何 server 块
2. **挂载**：各端自发发现机制，不注入；挂载探针先行（第①步清单即证据）
3. **交互**：纯自然语言驱动探针，禁注入工具调用
4. **网络**：真网关真 key；**curl 全序列前置门**——不过则整轮 ENV_FAIL 不入表（网络层问题不冒充兼容性）

### 3.3 判定态（五态，全部非门禁）

| 态 | 符号 | 判据 | 入表 |
|---|---|---|---|
| PASS | ✅ | transcript 存在非错误 `mcp__<server>__` 调用 | 兼容性列 |
| CALL_FAIL | ⚙ | 存在失败调用尝试（挂了调不动=客户端×网关问题，如 codex） | 兼容性列 + 错误签名 |
| NOT_MOUNTED | ⊘ | 挂载清单无该 server（客户端不挂载此类型=产品事实） | 兼容性列 |
| SETUP_BLOCKED | ⛔ | 授权/信任未通过、transcript 缺失 | 兼容性列 + 注记 |
| INFRA_FAIL | ❌ | 进程异常/前置门未过 | 不入表或标注 ENV_FAIL |

不进端健康度分母（与现有 NOT_MOUNTED 处理一致）；report_matrix 增设独立「M 组（HTTP MCP 兼容 · 宿主车道）」分组与兼容性列。

### 3.4 与现有体系的关系

- 既有评分链资产复用：transcript 提取 → adapter 解析 → assertor（require_ok 已修）
- docker 夜测管线（P/R/D 组）不动；M 组从 docker 车道迁出（容器内 M 记录全部已清，不回填）
- 结果记录沿用 schema 1.0，`run_id` 前缀 `host-<agent>-...` 区分车道

### 3.5 成本与节奏

- 每轮：15 个交互会话并行，1–3 分钟（上限 6 分钟）；token 消耗首轮实测后记录
- 触发：手动/按需（M 组不进常规夜测循环；重要变更后跑一轮）

## 四、不做的事

- 不做容器内全量 HOME 快照方案（oracle 方案 B 不采纳为主线——宿主车道更字面忠实且更便宜；B 的快照漂移/headless 校准成本无必要）
- 不做协议层拆测入矩阵（oracle 方案 C 的 curl 前置门吸收其价值）
- 不改 docker 夜测的 P/R/D 探针行为
- 不处理 codex×bigmodel 兼容性本身（用户明确：兼容的事不管，只测清楚）

## 五、验收口径

1. 首轮五端实测复现基准事实签名：codex ⚙×3（错误签名含 channel closed 或 Deserialize 之类调用失败证据）、其余四端 ✅ 或有因可查的 ⛔/⊘
2. report_matrix 呈现独立 M 组分组，五态符号正确，不计入门禁与健康度分母
3. 忠实度四维各有一条可检查证据（配置 diff 零/挂载清单/自然语言探针/curl 前置门日志）
4. 全套单测绿（新车道入口的判定态路由 + adapter 复用回归）

## 六、风险

| 风险 | 缓解 |
|---|---|
| PTY 交互自动化的端差异（提示符/超时/分页） | 每端适配层 + 6 分钟硬超时；首轮人工盯跑一次固化 |
| claude 项目批准依赖人工一次 | 首轮清单里明示；已批准项目免 |
| 宿主车道与用户日常使用互抢会话/配额 | 探针短小（每端 4 条消息），跑前提示 |
| 凭据/信任态随时间变化导致 ⊘/⛔ 漂移 | 判定态带原因注记，漂移可解释 |
