## 三、慢因定性（预置脚本缺失 / 模型思考 / 路径不确定性，各占多少）

### 1. 可量化分解

这里将“慢因占比”限定为从首个工具调用第 238 行 `02:38:34.091Z` 到最后工具结果第 6629 行 `02:44:33.317Z` 的 **359.226 秒**。三类慢因并非互斥：预置脚本缺失会把工作推给模型；路径不确定性会触发模型复盘和重试；因此不能把三项百分比机械相加。

| 慢因类别 | 证据 | 可量化金额 | 定性 |
|---|---|---:|---|

### 2. `pre-check.sh` 的职责边界为何导致模型变慢

当前脚本头部第 1–4 行声明：

- 处理 npx、uvx、ast-grep、codegraph、openspec CLI、pi-mcp-adapter；
- 不处理 Superpowers 软链、OpenSpec 四客户端产物、Playwright、API Key。

脚本末尾第 459–465 行只执行 `do_npx`、`do_uvx`、`do_ast_grep`、`do_codegraph`、`do_openspec`、`do_pi_mcp_adapter`。因此，虽然 SKILL.md 总体上把 OpenSpec 四端和 Superpowers 视为 pre-check 的强制步骤，真正的 shell 入口只覆盖基础工具；模型必须自行承担：

- 第 1253–1256 行的项目/HOME 状态探测；
- 第 2043–2046 行的 OpenSpec 初始化与 Superpowers 更新；
- 第 4078–5942 行的软链盘点、同步、逐项验证。

这正是“命令执行 8 秒但模型耗时 6 分钟”的结构性来源。优化不应继续压缩 `find`/`ln` 的毫秒，而应消除模型重新编程这些机械动作的必要性。

### 3. 模型等待的具体构成

1. **路径纠错**：第 236 行已经知道脚本位于 `.../pre-check/scripts`，但第 240 行仍查错误的 `<skill>/mirrors`；第 308、407 行继续排查。工具只 0.179 秒，阶段却 14.230 秒。
2. **完整脚本阅读**：第 816–817 行读取 486 行 shell 脚本，再由模型解释参数和实现；对于增量已就绪路径，脚本报告契约已经足够。
3. **重复状态探测**：第 1253–1256 行分别检查项目产物和 HOME；这些应由一个统一脚本报告一次输出。
4. **shell 方言失败分析**：第 2045 行失败后，到第 3322 行复盘间隔 55.768 秒；问题是 zsh 不对未加引号参数展开做空格分词。
5. **临时同步器设计/审查**：第 4078 行到第 4979 行等待 47.990 秒；第 4979 行到第 5941 行等待 48.263 秒。模型不仅写脚本，还要分析计数器和正确链误报。
6. **越界收尾**：第 6586–6629 行探测并写入 memory，新增 5.844 秒阶段跨度和非预期副作用。

### 4. `openspec init` 约 2.4 秒是否合理

**结论：本 fixture 上该量级合理，且产物证据证明执行完整；但严格说只能称为 init+update 命令链 2.441 秒。**

- 初始化前四端均为 0（第 1254 行），不是因为已有文件而秒跳过。
- OpenSpec 输出四端 `Setup complete`、`Created: Claude Code, Codex, Pi, Kimi Code`（第 2044 行）。
- 后续检查明确四端文件、目录和数量均符合预期（第 3323 行）。
- fixture 后验显示真实目录/文件均存在，包含约 95 个文件，且四端均有 OpenSpec 投影。
- 因而 2.441 秒符合“本地已安装 CLI + 本地文件写入”的合理量级，不是只打印成功。
- 但命令链中还包括 `openspec update`，所以不能把 2.441 秒当成 init 单独耗时。需要独立运行 `time openspec init ...` 才能回答 init 单项精确耗时。

### 2. 推荐脚本化边界

建议形成“两层契约”：

**模型层只做三件事：**

1. 确定 `PROJECT_ROOT`、脚本绝对路径、独占 report 路径；
2. 执行一次 `bash "<PRE_CHECK_SH>" run [--mirror ...] [--no-interrupt] --project-root "<PROJECT_ROOT>"`（具体接口名在实现阶段确定）；
3. 读取 JSON，中文呈现，不自行改写安装/更新/链接命令。

**脚本层完成所有确定性动作：**

- 六基础工具现有探测/安装逻辑；
- OpenSpec 四端检测、缺失端 init、`openspec update`、四端路径/数量验证；
- Superpowers 来源目录有效性、候选逐项 clone/fetch、origin 选择、当前分支 `pull --ff-only`；
- 第 2 层和第 3–5 层软链创建/更新/冲突处理/范围限定清理；
- 阶段级耗时、action、version、error、created/updated/skipped/conflicts；
- Playwright 继续显式 opt-in；API Key 继续只展示占位符，不写真实密钥。

脚本化不等于无条件覆盖：

- no-interrupt 冲突规则必须实现备份、创建、验证，任一步失败即失败；普通模式保留“不覆盖、警告、人工决定”。
- 只清理能证明属于 Superpowers 的失效链；不得按目录总数或简单前缀删除 Cadence/OpenSpec/用户条目。
- 候选必须在 Bash 内安全解析；禁止重用“Python `join(' ')` + 外层未加引号变量”的协议。

### 3. OpenSpec 纳入脚本 vs 保持模型执行

| 选择 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 纳入脚本 | 规则机械且明确；本 fixture 已证明四端路径/数量可断言；消除漏端/错分支 | 需要跟踪 CLI 版本和目录布局，处理已有文件冲突 | **推荐纳入** |
| 保持模型执行 | 改动小，CLI 变化由模型解释 | 本次在发起 OpenSpec+git 前就等待 33.305 秒；模型仍可能合并命令、截断输出、漏验证 | 仅作短期 fallback |
| 只脚本验证、模型写入 | 降低最终误报 | 写入仍受模型等待、shell 方言和跳步影响 | 不足以满足夜测确定性 |

### 4. Superpowers 纳入脚本 vs 保持模型执行

| 选择 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 纳入脚本 | Git 更新/浅克隆/软链都是明确副作用；解决 URL 拼接、计数 bug 和误判；可设置单候选/总 timeout | HOME 删除/替换风险高，必须严格所有权判定、fixture、dry-run、真机门禁 | **推荐纳入**，拆成 `superpowers-update` 与 `superpowers-sync` 两阶段 |
| 保持模型执行 | 能灵活理解冲突 | 本次首轮失败；同步脚本误报；模型阶段约 139 秒 | 不推荐 |
| 模型确认后脚本执行 | 普通模式可兼顾解释和确定性 | no-interrupt 仍多一回合 | 普通模式可选；eval/no-interrupt 直接脚本执行 |

### 5. 软链报告和断言建议

脚本应输出按 Superpowers 所有权范围计算的报告，而非让模型临时统计。示意：

````text
phase=superpowers
source=/home/.../.agents/superpowers/skills
source_entries=14
layers:
  - path=~/.agents/skills superpowers_links=14 correct=14 stale=0 broken=0 conflicts=0
  - path=~/.codex/skills/skills superpowers_links=14 correct=14 stale=0 broken=0 conflicts=0
  - path=~/.claude/skills superpowers_links=14 correct=14 stale=0 broken=0 conflicts=0
  - path=~/.pi/agent/skills superpowers_links=14 correct=14 stale=0 broken=0 conflicts=0
result=success
````

断言要点：

- `source_entries` 动态读取，不永久写死 14；
- 每个源条目在四层均为软链且目标存在；
- 第 2 层指向真实 Superpowers 源，第 3–5 层指向第 2 层规范入口；
- broken/stale/conflict 只按 Superpowers 条目统计；
- 非 Superpowers 条目前后不变；
- 普通模式冲突为 warning/partial，no-interrupt 冲突为 failed；
- 计数器必须在同一 Bash 进程中累积，禁止管道子 shell 丢状态。

### 6. 迁移顺序

1. 先抽取纯检查：fixture 锁定 OpenSpec 四端、Superpowers 来源和四层所有权断言。
2. 再抽取写入：把 OpenSpec init/update 与 Superpowers update/sync 放入脚本子命令；候选解析全部留在 Bash 内。
3. 保留兼容 fallback：主脚本 `unsupported` 时明确报告需人工处理，不静默回到模型自由发挥。
4. 报告增加 `duration_ms`：分别记录 base-tools、openspec、superpowers-git、superpowers-links、verification。
5. 最后缩短 SKILL.md：保留契约、参数、失败语义和人工 fallback，删除让模型临时编程的长 one-liner/heredoc。

### 7. 目标耗时的现实表述

- 当前 fixture 已装基础工具、已有 Superpowers 仓库、网络可达、四端 OpenSpec 缺失时，机械动作约为：基础脚本 0.550 秒 + OpenSpec init/update 2.441 秒 + Superpowers 成功 fetch/pull 4.598 秒 + 软链盘点/同步/验证 0.360 秒，约 **7.949 秒**（不含独立状态探测和报告命令）。
- 若来源目录不存在，浅克隆耗时取决于网络；不能用本次已有仓库的 4.598 秒代替。脚本需要单候选 timeout、总 timeout、逐候选错误。
- “2–3 分钟”应作为**已安装工具/已有 Superpowers 仓库的增量运行整体目标**，不是所有冷启动网络场景的机械耗时承诺。冷启动网络场景应以独立预算和失败快返为准。

## 五、对 eval 夜测的影响（timeout 预算、确定性断言影响）

### 1. timeout 预算建议

建议把 eval 的 wall-clock timeout 与脚本内部网络 timeout 分层：

| 层级 | 建议预算 | 依据与目的 |
|---|---:|---|
| 基础工具脚本 | 已就绪增量 30 秒；缺失工具安装 2–5 分钟 | 本次已就绪 `run --mirror cn --no-interrupt` 只耗 0.550 秒（第 929–930 行）；安装才受 npm/pip 网络影响 |
| OpenSpec 本地阶段 | 30 秒 | 本次 init+update 2.441 秒（第 2043–2044 行）；用于发现 CLI 卡住/交互，不应无限等 |
| Superpowers Git | 单候选 30–60 秒；总阶段 2–3 分钟 | 已有仓库成功 fetch+pull 4.598 秒（第 3324–3327 行）；冷启动 clone 需独立预算 |
| Superpowers 软链+验证 | 30 秒 | 本次相关工具执行仅 0.360 秒（第 4078–5942 行）；超时更可能是脚本 bug/死循环 |

- **增量就绪 suite**：基础工具和 Superpowers 来源已准备，验证 OpenSpec 补齐与 Superpowers update/sync；目标 2–3 分钟，硬上限 4 分钟。
- **冷启动 suite**：允许 clone/npm/pip 网络，timeout 5–10 分钟；但必须要求完整阶段报告，不能用宽松 timeout 接受跳步。

#### 基础工具

- 脚本退出码为 0；JSON `overall == success`；

#### Superpowers Git

- 来源目录存在且是有效 Git work tree；

- 候选 URL 必须逐个解析，不得出现第 2046 行 malformed concatenated URL；
- 网络失败必须是 failed/partial，不得静默回退本地目录。

#### 四层软链

- 源条目动态枚举（本次为 14）；
- 每个条目在 `~/.agents/skills`、`~/.codex/skills/skills`、`~/.claude/skills`、`~/.pi/agent/skills` 均为可解析软链；
- broken/stale/conflict 只按 Superpowers 范围统计；

- 不比较四层总数相等。第 5942 行 pi 总数 27、第 6134 行说明差异是非 Superpowers 的 `knowledge-base-context`；总数断言会误报；
- 输出 created/updated/skipped/conflicts，且计数在同一 Bash 进程累积。

#### 失败路径

至少增加以下负向 fixture：

1. 基础工具失败：no-interrupt 立即失败且不创建下游产物。
2. OpenSpec 仅缺 pi 或 kimi：只 init 缺失端再 update，已就绪端不应被覆盖。
3. Superpowers 来源不存在：候选逐一 clone，失败清理临时目录并返回失败。
4. 来源非 Git：立即失败，不把本地任意目录当 fallback。
5. 外层 shell 为 zsh 且候选有多个 URL：脚本内部仍解析为多个候选，不拼接。
6. 四层已有正确链：结果为 skipped，不无意义重写。
7. 同名非软链：普通模式 warning/skip；no-interrupt 按备份→创建→验证执行，原内容不删除。
8. pi 层缺 Cadence skill：Superpowers phase 仍可 success，不为总数相等擅自补链。
9. Playwright 未请求：不安装、不写 skills。
10. 成功、失败、超时均清理独占 report；失败先输出结构化错误再清理。

### 4. 对五个必核实疑点的最终结论

1. **SKILL.md 全步骤 vs transcript**：基础工具、OpenSpec、Superpowers update、四层链、Playwright 跳过、API Key 提醒最终都有证据；但路径排查、git 首轮、软链同步实现存在简化/自由发挥。OpenSpec 四端没有跳过，fixture 证明真实落盘。
2. **OpenSpec 2.4 秒是否合理**：合理，但准确说是 init+update 2.441 秒；fixture 前缺失、命令输出成功、后验四端目录/文件/数量齐全，证明不是未完整执行。
3. **四段 heredoc 做什么**：第 3324 行做 Superpowers Git 重试；第 4078 行做来源/四层盘点；第 4979 行做四层软链同步；第 5941 行做逐项验证。它们工具总耗时仅 4.958 秒，但相关模型设计/等待超过 139 秒，完全可以预置为脚本；第 6133 行另有一段短 heredoc 做收尾探测，不属于四个核心动作。
4. **两次真实执行差异**：背景中的“历史一次 3 URL 拼接失败、约 3 秒 Already up to date”与当前 transcript 不应混用；当前 transcript 也出现同类拼接失败，但随后用 Bash 重试，成功 update 耗时 4.598 秒。当前 transcript 不支持“本次直接跳过 git update”；如要断言两次差异，需补齐上一运行的原始 transcript。

### 5. 最终建议
