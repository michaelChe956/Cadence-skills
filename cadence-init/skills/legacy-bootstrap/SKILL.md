# Legacy Bootstrap v2.0

## 概述

使用 `npx repomix@latest` 汇总当前本地 legacy 项目上下文，通过**类型驱动的产物管线**分析项目结构、架构、模块、依赖、风险和未知项，并将结果逐一沉淀到目标项目的 `cadence/` 目录。

该 skill 属于 `cadence-init` 插件，面向已经在 Claude Code 或 Codex 中打开的本地 clone 项目。

## 核心原则

- 只处理当前打开的本地项目，不 clone 远程仓库。
- 默认使用 `npx repomix@latest`。
- 所有认知产物写入 `cadence/`，不生成 `.ai/`。
- **逐产物生成，边做边报告**，禁止批量输出后遗漏。
- **按项目类型条件触发专属产物**，确保覆盖完整。
- 产物生成完成后必须更新 `CLAUDE.md` 与 `AGENTS.md`。
- 不直接重构业务代码。
- 不把未知业务事实写成确定结论。
- `--skill-generate` 只作为结构参考，不作为主流程。

## 何时使用

### 使用场景

- 用户要求为 legacy 项目初始化项目认知。
- 用户要求使用 repomix bootstrap 当前项目。
- 用户要求生成架构、模块、风险、构建测试画像等 Cadence 文档。
- 进入历史项目并计划修改前，需要先建立项目认知。
- 当前 Claude Code 或 Codex 已经打开目标项目的本地 clone。

### 不使用场景

- 目标是全新空项目，没有 legacy 代码或历史结构需要梳理。
- 用户只要求查看少量文件或回答局部问题。
- 用户明确要求不生成 Cadence 文档。
- 用户要求分析远程 GitHub 仓库，但没有提供或打开本地 clone。

## 整体流程架构

```
Phase 1: 环境检测
  ├─ 确认项目根目录
  ├─ 读取项目规则（CLAUDE.md / AGENTS.md）
  └─ 运行 repomix 生成快照

Phase 2: 项目类型识别
  ├─ 从 repomix 输出中提取信号（框架、依赖、目录结构）
  ├─ 判定项目类型（可多选，取并集）
  ├─ 向用户展示判定结果并请求确认
  └─ 确定产物清单 = 核心产物 + 类型专属产物

Phase 3: 逐产物生成管线
  ├─ 按清单顺序，逐个产物：
  │   ├─ 从 repomix 提取相关信息
  │   ├─ 写入 cadence/ 对应路径
  │   └─ 输出确认行："✓ [N/总数] 已生成: <路径>"
  └─ 若某产物证据不足 → 输出："⚠ [N/总数] 跳过: <产物名> — 原因: <说明>"

Phase 4: 收尾验证 + 报告
  ├─ 检查所有应生成文件是否存在于磁盘且非空
  ├─ 更新 CLAUDE.md / AGENTS.md 认知链接
  └─ 输出 Bootstrap 汇总表
```

## Phase 1: 环境检测

### 1.1 确认目标项目根目录

读取目标项目规则前，必须先确认当前工作目录是目标项目根目录。判断信号包括：

- `.git`。
- 主项目清单或包管理文件，例如 `package.json`、`Cargo.toml`、`pyproject.toml`、`go.mod`、`pom.xml`、`build.gradle`。
- 常见项目配置文件，例如 `Makefile`、`README.md`、`tsconfig.json`、`vite.config.*`、`docker-compose.yml`。

如果无法判断当前目录是否为目标项目根目录，先询问用户确认；确认不是根目录时停止执行，提示用户在目标项目根目录重新运行，不要对上级目录或不确定目录写入产物。

### 1.2 读取目标项目规则

在目标项目根目录优先读取：

- `CLAUDE.md`
- `AGENTS.md`
- `.claude/rules/document-storage.md`
- `.claude/rules/markdown-format.md`
- `.claude/rules/code-usage.md`
- `cadence/project-rules/README.md`

如果目标项目没有 Cadence 规则文件，使用默认目录约定：所有项目认知产物写入 `cadence/` 下对应子目录，入口规则写入根目录 `CLAUDE.md` 与 `AGENTS.md`。

读取规则时只采纳与当前 bootstrap 相关的约束；不得修改目标项目 `.claude/rules/` 中的框架规则文件。

### 1.3 确认执行模式

向用户确认是否使用深度模式：

- 用户选择深度模式：在标准模式基础上，按模块级粒度拆分更多文档。
- 用户未选择或未明确要求：执行标准模式。
- 若 repomix 输出 > 200,000 tokens 或文件数 > 100，建议深度模式。
- 用户可指定 `--deep` 或 `--standard`。

### 1.4 执行 repomix

基础命令：

```bash
npx repomix@latest --output cadence/analysis-docs/YYYY-MM-DD_分析资料_repomix-output_v1.0.xml
```

执行 repomix 前必须先检查 `cadence/analysis-docs/` 是否存在；如果不存在，应先创建该目录。

建议使用 `--ignore` 避免把已有 repomix 输出、历史分析产物、生成物、缓存和大型构建目录重新打包：

```bash
npx repomix@latest \
  --ignore "**/repomix-output*.xml,cadence/analysis-docs/*repomix-output*.xml,cadence/analysis-docs/*分析资料*.xml,node_modules,dist,build,coverage,.next,.turbo,target,tmp,cache,.cache" \
  --output cadence/analysis-docs/YYYY-MM-DD_分析资料_repomix-output_v1.0.xml
```

项目较大时优先考虑以下选项：

- `--compress`
- `--include`
- `--ignore`
- `--split-output`
- `--token-count-tree`

如果 `npx` 不可用，提示用户先运行 `/pre-check` 或安装 Node.js/npx。

如果 repomix 失败，必须记录失败原因、已执行命令和建议重试命令；不得在缺少 repomix 证据时编造分析文档。

### 1.5 参考 repomix skill-generate（可选）

`--skill-generate` 是 repomix 的实验能力，只能作为结构参考。

可参考内容：目录组织方式、触发描述写法、上下文拆分方式。

禁止事项：
- 不能把 `--skill-generate` 作为本 skill 的默认主流程。
- 不能把 `--skill-generate` 输出直接作为最终产物。

## Phase 2: 项目类型识别

### 2.1 类型检测信号

从 repomix 输出中提取以下信号，判定项目类型：

| 项目类型 | 检测信号 |
|---------|---------|
| **前端应用** | `package.json` 含 react/vue/angular/svelte 依赖；存在 `src/components/`、`src/pages/`、`app/` 等目录；有 vite/webpack/next 配置 |
| **后端服务（单体）** | `Cargo.toml`/`go.mod`/`pom.xml`/`package.json` 含 express/fastify/nest；存在 `src/routes/`、`src/handlers/`、`controllers/`；有数据库依赖 |
| **后端服务（微服务）** | 多个独立服务目录各有自己的入口/配置；存在 docker-compose 多服务定义；有 API 网关/服务注册/消息队列依赖 |
| **全栈应用** | 同时满足前端 + 后端信号；或使用 Next.js/Nuxt/Remix 等全栈框架 |
| **CLI/工具库** | `bin/` 目录；`package.json` 有 `bin` 字段；`Cargo.toml` 有 `[[bin]]`；存在 `commands/`、`cli/` 目录 |
| **基础设施/DevOps** | 存在 `.tf` 文件、`k8s/`、`helm/`、`Dockerfile`、`ansible/`、`pulumi/` |

### 2.2 组合规则

- 一个项目可匹配多个类型，产物清单取**并集**。
- 例：Cadence Aria → 后端单体（Rust/Actix）+ 前端应用（React）→ 生成两者的专属产物。
- 若无法识别类型 → 回退为"未知类型"，只生成核心产物，并在报告中标注。

### 2.3 用户确认

类型识别完成后，**必须**向用户展示判定结果并请求确认：

> "检测到项目类型：**<类型1> + <类型2>**。将生成核心产物 8 项 + <类型1>专属 N 项 + <类型2>专属 M 项，共 X 项。确认？"

用户可修正类型判定（如"这其实是微服务"），修正后重新计算产物清单。

### 2.4 确定产物清单

根据确认的项目类型，计算最终产物清单：

```
最终产物清单 = 核心产物(8项) + 所有匹配类型的专属产物(并集)
```

### 3.2 逐产物生成协议

对产物清单中的每一项，严格执行以下三步：

**Step 1: 提取** — 从 repomix 输出中定位与该产物相关的代码、配置、依赖声明等片段。

**Step 2: 写入** — 基于提取的证据生成文档，写入 `cadence/` 对应路径。文档内容必须：
- 有证据支撑，不编造
- 证据不足的信息标记为 `[UNKNOWN]`、`[TODO]` 或 `[NEED_CONFIRMATION]`
- 内容充实（> 100 字符），不允许只有标题的空文档

**Step 3: 确认** — 输出一行状态报告：

```
✓ [1/15] 已生成: cadence/architecture/2026-05-27_架构文档_系统总览_v1.0.md
✓ [2/15] 已生成: cadence/architecture/2026-05-27_架构文档_模块地图_v1.0.md
⚠ [3/15] 跳过: 数据模型 — 原因: 项目无持久化层，纯内存计算
✓ [4/15] 已生成: cadence/docs/2026-05-27_约束文档_风险区域与遗留陷阱_v1.0.md
...
```

### 3.3 产物内容详细程度

所有产物的详细程度要求为**端点清单级别**：

- **API 文档**：列出所有 API 路径、方法、请求/响应结构、认证要求，类似精简版 Swagger
- **组件文档**：列出所有核心组件的 props 接口、事件、插槽
- **数据模型**：列出所有核心实体的字段、类型、关系
- **模块地图**：列出所有模块的边界、导出接口、依赖方向

不能只写概述性描述，必须列出具体条目。

### 3.4 禁止行为

- ❌ **禁止将多个产物合并到一个文件中** — 每个产物必须是独立文件
- ❌ **禁止静默跳过产物** — 跳过必须报告原因
- ❌ **禁止生成空文件或只有标题的文件** — 文件内容必须 > 100 字符
- ❌ **禁止编造无证据支撑的内容** — 不确定的用 `[UNKNOWN]` 标记

## Phase 4: 收尾验证 + 报告

### 4.1 磁盘验证

所有产物生成完毕后，执行磁盘验证：

1. 遍历产物清单，检查每个"已生成"文件是否真实存在于磁盘。
2. 检查文件非空（> 100 字符）。
3. 若发现缺失或空文件 → 重新生成该产物。
4. 验证全部通过后进入下一步。

### 4.2 更新入口文档

产物完成后必须更新目标项目根目录的 `CLAUDE.md` 与 `AGENTS.md`。

更新方式是新增或更新 `Legacy 项目认知` 区域，按以下分层结构组织：

```markdown
## Legacy 项目认知

### 首选入口

- `<Bootstrap 总结路径>`
- `<系统总览路径>`
- `<模块地图路径>`

### 修改代码前必须读取

- 构建与测试：`<构建测试画像路径>`
- 风险区域：`<风险与约束路径>`

### 类型专属文档

- API 端点：`<API 文档路径>`
- 组件接口：`<组件文档路径>`
- 服务依赖：`<服务依赖关系路径>`
- ...（按实际生成的类型专属产物列出）

### 使用规则

- 本区域只列出实际生成的 Cadence 文档，不链接未生成的候选路径。
- 不确定内容以 `[UNKNOWN]`、`[TODO]`、`[NEED_CONFIRMATION]` 为准。
- 不得把 bootstrap 初稿视为绝对事实。
- 发现文档与代码不一致时，优先相信当前代码，并更新对应 Cadence 文档。
```

只链接实际生成的文档，不链接跳过的。使用相对路径。

如果 `CLAUDE.md` 或 `AGENTS.md` 不存在，应创建最小入口文档。

### 4.3 输出 Bootstrap 汇总表

```
┌─────────────────────────────────────────────────────────────┐
│ Legacy Bootstrap 产物汇总                                    │
├──────────┬──────────┬───────────────────────────────────────┤
│ 状态     │ 数量     │ 说明                                  │
├──────────┼──────────┼───────────────────────────────────────┤
│ ✓ 已生成 │ 13       │                                       │
│ ⚠ 跳过   │ 2        │ 数据模型、状态管理（附原因）           │
│ 总计     │ 15       │ 核心8 + 前端4 + 后端3                 │
└──────────┴──────────┴───────────────────────────────────────┘
```

汇总表后附加：

- repomix 输出文件路径
- 项目类型判定结果
- `[UNKNOWN]`/`[TODO]`/`[NEED_CONFIRMATION]` 摘要
- 建议下一步

## 深度模式

### 标准模式 vs 深度模式

| 维度 | 标准模式 | 深度模式 |
|------|---------|---------|
| 核心产物 | 全部生成 | 全部生成 |
| 类型专属产物 | 全部生成 | 全部生成 |
| 粒度 | 系统级（一个模块地图覆盖所有模块） | 模块级（每个核心模块单独一份分析文档） |
| 额外产物 | 无 | 每个核心模块：模块分析 + 风险分析 + 领域模型 |
| 适用场景 | 中小项目、快速了解 | 大型项目（>50 文件）、需要深入改造 |

### 深度模式额外产物

对项目中识别出的每个**核心模块**（通常 3-10 个），额外生成：

| 路径 | 内容 |
|------|------|
| `cadence/architecture/YYYY-MM-DD_架构文档_<模块名>模块分析_v1.0.md` | 单个模块的职责、边界、依赖、内部结构和修改风险 |
| `cadence/analysis-docs/YYYY-MM-DD_分析报告_<模块名>风险分析_v1.0.md` | 单个模块的风险点、历史包袱和验证建议 |

深度模式的额外产物同样遵循逐产物生成协议（提取→写入→确认）。

### 模式选择逻辑

- 默认询问用户选择模式。
- 若 repomix 输出 > 200,000 tokens 或文件数 > 100，主动建议深度模式。
- 用户可指定 `--deep` 或 `--standard`。
- repomix 输出过大、无法处理或时间受限时，可降级为轻量模式（只生成核心产物，跳过类型专属）。

## 错误处理

| 错误 | 处理方式 |
|------|----------|
| 当前目录不是项目根目录 | 检查 `.git`、主项目清单文件和常见配置文件；无法判断时询问用户确认。确认不是根目录后停止执行 |
| `npx` 不可用 | 提示用户运行 `/pre-check` 或安装 Node.js/npx；不要继续执行 |
| repomix 失败 | 记录失败原因、命令和建议重试命令；不要编造分析文档 |
| repomix 输出过大 | 优先使用 `--compress`、`--include`、`--ignore`、`--split-output` 缩小范围；必要时降级轻量模式 |
| `cadence/` 不存在 | 创建 `cadence/` 及所需子目录 |
| `CLAUDE.md` 或 `AGENTS.md` 不存在 | 创建最小入口文档 |
| 信息证据不足 | 使用 `[UNKNOWN]`、`[TODO]`、`[NEED_CONFIRMATION]` 标记 |
| 产物收尾验证失败 | 重新生成缺失/空文件，再次验证 |
