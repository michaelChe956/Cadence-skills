# 渐进式双轨读取指南

## 目录

- 输入与证据边界
- 七层读取算法
- 实体映射
- 画像深化
- 双轨对照
- 停止判断

## 输入与证据边界

先从 Manifest 取得唯一授权范围，再建立两条同等重要的证据路径：

| 路径 | 负责回答 | 典型来源 |
|------|----------|----------|
| KnowledgeBase | 系统定义了什么、实体如何命名、关系和业务语义是什么 | `README.md`、领域索引、稳定 ID、关系矩阵、证据索引、待确认项 |
| 当前实现 | 当前提交实际如何运行、入口在哪里、哪些文件和符号受影响 | 源码、DDL、SQL、有效配置、测试、Git Diff |

不得用 KnowledgeBase 代替当前实现，也不得用当前实现抹去用户资料和业务语义。

## 七层读取算法

### 第 0 层：前置校验

读取规则、Manifest、当前 Git 提交和工作区状态。校验：

- `schema_version` 必须为 `3.0`。
- 目标工程和领域必须在 Manifest 范围内。
- 记录 `baseline_commit`、当前提交和未提交变更。
- 领域为 `不适用` 时停止该方向读取。

### 第 1 层：任务种子

从请求抽取并去重：

- 业务术语和用户动作。
- 页面、路由、API、能力编码、服务、表、中间件、配置键。
- 文件、类、方法、错误码、日志关键词、测试名称。
- 用户限定的工程、模块和交付目标。

优先级：精确文件或稳定 ID > Method + Path / 符号 > 业务术语 > 模糊名称。

### 第 2 层：双轨定位

KnowledgeBase 路径：

1. 从 `README.md` 和领域 `README.md` 定位候选稳定 ID。
2. 读取候选实体主文件，不批量加载同目录全部文档。
3. 从追溯矩阵取得直接上下游和证据位置。

当前实现路径：

1. 从用户点名文件、符号、路由或配置开始。
2. 使用结构化大纲确认候选定义，再读取必要实现区间。
3. 对 REST 合并 Method、Path、`baseURL`、代理和网关重写。
4. 对数据访问核对 DDL、SQL、Entity、Mapper 和迁移文件。

### 第 3 层：一跳扩展

只读取种子实体的直接关系：

| 种子 | 默认一跳 |
|------|----------|
| PAGE / ROUTE | 请求函数、Store/Hook、API |
| API | Controller/Provider、Service、鉴权、参数与错误 |
| SERVICE / MODULE | 直接调用、DAO、RPC、消息、文件、事务 |
| TABLE | Entity、Mapper、SQL、DDL、直接写入服务 |
| MIDDLEWARE | Producer/Consumer、配置、序列化、重试 |
| TEST | 被测符号、Fixture、Mock、测试配置、执行命令 |
| Git Diff | 修改符号、直接调用方、相关测试和配置 |

以下关系默认停止：通用日志、基础异常、无业务分支的工具类、框架启动链、全局依赖树。

### 第 4 层：画像深化

逐项检查主辅画像的专属输出字段。只有缺失字段会影响下游判断时，才沿对应关系再扩一跳。

示例：Coding 已定位 Controller、Service 和 SQL，但没有异常处理与测试入口，则只深化异常分支和测试，不继续扫描无关调用方。

### 第 5 层：双轨对照

为每个关键结论建立：

| 结论 | KnowledgeBase 证据 | 当前实现证据 | 状态 | 任务影响 |
|------|--------------------|--------------|------|----------|

状态判定：

| 状态 | 判定 |
|------|------|
| `一致` | 两侧结论可相互验证 |
| `KnowledgeBase 缺失` | 当前实现存在，知识库未登记或未覆盖 |
| `源码缺失` | 知识库或用户资料声明存在，当前范围未定位实现 |
| `基线漂移` | 当前提交晚于基线，相关实体已发生变化或需要复核 |
| `来源冲突` | 两侧对同一事实给出不兼容结论 |
| `待确认` | 证据不足或候选无法唯一映射 |

不要把“当前提交晚于基线”自动等同于所有实体漂移；必须核对任务相关文件或符号是否在基线后变化。

### 第 6 层：停止与压缩

停止后只保留：

- 任务直接相关实体。
- 一跳关系和为补齐画像字段而增加的必要关系。
- 能定位事实的稳定 ID、路径、符号、行号或配置键。
- 冲突、漂移、缺口和假设。

删除无关历史、完整源码副本、重复描述和不影响任务的公共基础设施。

## 实体映射

稳定 ID 与当前实现之间按以下证据匹配：

1. 文档记录的精确源码位置。
2. REST `HTTP Method + 规范化 Path`。
3. 能力编码、消息 Topic、任务名称、配置键等唯一标识。
4. 类、方法和调用链组合。
5. 业务名称只用于生成候选，不单独完成映射。

同名候选超过一个时列出差异并询问用户。

## 基线与未提交变更

- 使用 Git 比较 `baseline_commit..HEAD` 中与任务种子相关的文件和符号。
- 未提交修改作为当前实现的一部分进入证据矩阵，并明确标记 `工作区修改`。
- 不恢复、暂存或清理用户修改。
- KnowledgeBase 已过期时只建议 `knowledge-base-update`，本 Skill 不执行更新。

## 冲突处理矩阵

| KnowledgeBase | 当前实现 | 输出方式 |
|---------------|----------|----------|
| 有定义且实现一致 | 有证据 | `一致`，可直接供下游使用 |
| 有业务定义 | 未定位实现 | `源码缺失`，区分未实现、范围外和定位失败 |
| 无登记 | 有实现 | `KnowledgeBase 缺失`，说明是否可能为新增或内部能力 |
| 定义与实现不一致 | 有冲突证据 | `来源冲突`，分别陈述意图和行为 |
| 基线后相关文件变化 | 有当前证据 | `基线漂移`，以后者描述当前行为但保留原语义 |

## 就绪判断

- `就绪`：画像必需字段齐全，实体唯一，关键关系和验证入口明确。
- `有条件就绪`：缺失项不改变方向，已给出清晰假设和补证方式。
- `阻断`：实体无法唯一确定、范围未授权、关键业务规则缺失或来源冲突会改变方案。
