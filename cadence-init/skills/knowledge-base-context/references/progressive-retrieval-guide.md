# Schema 4.0 四类证据渐进读取指南

## 目录

- 输入与授权边界
- 八层读取算法
- 四类路径
- 表与配置关系门禁
- 基线与变更包
- 证据矩阵与停止判断

## 输入与授权边界

只接受 `cadence/knowledge-base/manifest.yaml` 中的 `schema_version: "4.0"`。Manifest 缺失或不是 4.0 时停止，不兼容、不迁移，也不回退全仓分析。

读取开始前固定取得：

| Manifest 区域 | 用途 |
|---------------|------|
| `scope.projects` | 工程与仓库授权边界 |
| `scope.data_models` | 数据库、Schema、逻辑表与排除范围 |
| `scope.configurations` | 环境、服务、文件与配置来源授权边界 |
| `evidence.data_model_sources` | DDL、迁移、Entity、Mapper、SQL 和人工资料状态 |
| `evidence.configuration_snapshots.baseline` | 当前配置快照、外部只读目录、环境、发布批次、授权指纹与可审计范围摘要 |
| `update.last_change_package` | 最近处理变更包 |
| `update.processed_packages` | 已纳入 KnowledgeBase 的变更包集合 |
| `git.repositories` | 分支、Git 基线与仓库范围 |

外部配置目录不属于 KnowledgeBase，只能在授权范围内只读。敏感配置只记录键、用途、状态和绑定位置，值写为 `<redacted>`。

## 八层读取算法

### 第 0 层：Schema 与基线门禁

1. 校验 Schema 4.0、工程范围、数据模型范围和配置范围。
2. 读取数据模型来源状态、配置授权指纹、最近处理变更包和 Git 基线。
3. 记录当前分支、提交和工作区状态。
4. 对状态为 `不适用` 的领域记录原因并停止该方向。

配置为 `全量` 或 `指定` 且任务依赖实际配置时，授权指纹、`scope_summary`、纳入文件数量或清单摘要、服务摘要和文件规则摘要必须存在并与授权一致，外部目录必须可读且未越界，同一 `snapshot_id` 不得映射到不同环境或目录。此处只校验 Manifest 元数据；确定任务存在直接配置关系后，仍必须执行第 5 层的读取前/后双重指纹门禁。配置为 `不适用` 时记录原因并停止配置方向，不要求基线。

### 第 1 层：任务种子

从请求抽取并去重：

- 业务术语和用户动作。
- 页面、路由、API、服务、逻辑表、字段、数据源、配置组和配置键。
- 文件、类、方法、错误码、日志关键词、测试名称和目标环境。
- MR、分支、提交和显式 `CHANGE-*` 变更包。

优先级：精确路径或稳定 ID > Method + Path / 符号 / 表 / 配置键 > 业务术语 > 模糊名称。

### 第 2 层：知识库语义路径

```text
README → 领域索引 → 稳定 ID → 关系矩阵
```

1. 从总入口和相关领域索引定位候选稳定 ID。
2. 只读取候选实体主文件，不批量加载同目录文档。
3. 从关系矩阵取得 PAGE、API、SERVICE/MODULE、TABLE、配置组和变更历史的一跳关系。

### 第 3 层：当前代码路径

```text
任务对象 → 文件/符号 → 调用链 → 测试
```

1. 从用户点名文件、符号、路由或稳定 ID 的证据位置开始。
2. 用结构化大纲确认定义，只读取必要实现区间。
3. 对 REST 合并 Method、Path、`baseURL`、代理和网关重写。
4. 定位直接调用链、错误路径、测试和当前工作区修改。

当前代码路径不承担数据库真实结构或实际配置生效的证明责任。

### 第 4 层：数据模型路径

```text
TABLE → 字段级模型 → Mapper/SQL/Entity → DDL/迁移
```

1. 从关系矩阵或代码中的表、Mapper、SQL、Entity 定位逻辑表稳定 ID。
2. 读取该逻辑表的字段级文档，核对字段、类型、可空、默认值、主键、索引、约束、分片和来源状态。
3. 读取任务直接相关的 Mapper statement、SQL、Entity 映射和数据源路由。
4. 从 `evidence.data_model_sources` 定位相关 DDL 或迁移，只读取目标表、字段和约束片段。

DDL 可以缺失。存在字段级文档、迁移或代码结构证据时继续，并把无法确认的数据库属性标记 `数据模型证据缺失` 或 `待确认`。不得用 Entity 或 SQL 推断真实类型、默认值、可空性、索引或外键。

### 第 5 层：配置路径

```text
服务/配置组 → 配置键 → 当前快照文件 → 绑定代码 → 生效条件
```

1. 从服务配置文档定位配置来源、加载顺序、Profile、配置组和键。
2. 先确定任务与配置存在直接关系；没有直接关系时记录后停止，不得为了计算指纹读取外部快照。
3. 读取任何外部配置内容前，确认 Manifest 授权指纹和可审计范围摘要存在、非空且互相一致，外部目录存在、可读且位于授权范围内。
4. 确认同一 `snapshot_id` 没有环境或目录映射冲突。
5. 按 Schema 4.0 固定算法计算读取前最终快照指纹，并与 `evidence.configuration_snapshots.baseline.fingerprint` 比较。该计算只用于完整性校验，不产生配置结论。
6. 只有读取前指纹等于 Manifest 授权指纹时，才读取当前授权快照中与相关服务、配置组和键直接对应的文件，不遍历无关配置内容。
7. 核对 `@ConfigurationProperties`、`@Value`、Bean 工厂、条件注解、前端环境变量或客户端创建位置，并结合目标环境、Profile、覆盖顺序、条件装配和实际调用判断生效条件。
8. 相关配置读取完成后，按相同固定算法再次计算读取后最终快照指纹。
9. 写入任何实际配置结论前，必须满足 `读取前指纹 == 读取后指纹 == Manifest 授权指纹`。
10. 数据源或分片配置继续关联到数据源、Schema 和逻辑表稳定 ID，但不把路由配置当作数据库真实结构。

配置键存在不等于配置已生效。只有键或绑定、但缺少加载链和生效条件时，标记 `配置证据缺失` 或 `待确认`。

Manifest 指纹缺失或为空、目录不存在或不可读、目录越界、读取前比较失败、读取期间目录变化或读取后比较失败时，立即停止配置读取和配置结论输出，只报告阻断原因。重新计算的指纹不得写回或覆盖 Manifest，不得替换授权基线。

### 第 6 层：变更包与基线对照

1. 用 Git 比较 `baseline_commit..HEAD` 中与任务种子相关的文件和符号。
2. 从 `last_change_package` 和 `processed_packages` 判断最近已处理包是否与任务直接相关。
3. 相关时读取该包的 `change-summary.md`、`code-change.md`、`database-change.md`、`configuration-change.md` 和 `verification.md`。
4. 用户点名未处理包时读取该包，输出 `基线漂移`；不得替它执行 Update 或写入 Manifest。
5. 无直接关系时记录“最近处理变更包与任务无直接关系”，停止变更包方向，不扫描全部更新包。

### 第 7 层：画像深化、压缩与停止

逐项检查主辅画像的专属字段。只有缺失字段会改变下游判断时，才沿对应路径再扩一跳。

停止后只保留：

- 任务直接相关实体。
- 四条路径的最小充分证据。
- 表和配置关系的检查结论。
- 稳定 ID、路径、符号、字段、配置键、变更包和必要行号。
- 冲突、漂移、缺口、假设和就绪状态。

删除无关历史、完整源码副本、快照内容、重复描述和公共基础设施。

## 表与配置关系门禁

每次任务都必须检查两个方向，不因用户未点名表或配置而跳过：

| 任务种子 | 表关系检查 | 配置关系检查 |
|----------|------------|--------------|
| PAGE / ROUTE | `PAGE → API → SERVICE/MODULE → TABLE` | `PAGE → API → SERVICE/MODULE → 配置组/配置键` |
| API | Controller/Provider → Service → Mapper/SQL/TABLE | Controller/Service → Properties/Bean/客户端 → 配置键 |
| SERVICE / MODULE | DAO、Repository、Mapper、SQL、数据源路由 | 配置组、Profile、条件装配、客户端或数据源创建 |
| TABLE | 读写 Service、Mapper、SQL、数据源 | 数据源、Schema、分片和路由配置 |
| 配置键 | 绑定代码与调用链是否访问表或数据源 | 来源文件、覆盖顺序、绑定、生效条件 |
| TEST | Fixture、SQL、目标表与数据库约束 | 测试 Profile、覆盖文件、环境差异和条件装配 |

没有直接表关系时写“无直接表关系”，停止数据模型方向。没有直接配置关系时写“无直接配置关系”，停止配置方向。该结论不授权扫描其他表、服务配置或全部外部快照。

## 画像强制检查

- Review：同时核对 MR/提交范围、当前代码、数据库文档、配置文档、完整变更包和验证记录；任何一侧缺失或不一致必须进入证据矩阵。
- Debug：同时核对目标环境配置快照、配置生效条件、数据源路由、执行 SQL、字段值/字段状态和相关变更包；事实与候选根因分开记录。

## 四类证据矩阵

固定使用：

| 结论 | KnowledgeBase | 当前代码 | DDL/数据模型证据 | 配置快照证据 | 状态 | 任务影响 |
|------|---------------|----------|------------------|--------------|------|----------|

状态判定：

| 状态 | 判定 |
|------|------|
| `一致` | 任务所需各类证据可相互验证；不相关列明确写“无直接关系” |
| `KnowledgeBase 缺失` | 当前事实存在，但知识库语义或稳定 ID 未覆盖 |
| `代码缺失` | 知识库或用户资料声明存在，当前范围未定位实现 |
| `数据模型证据缺失` | 任务依赖结构事实，但字段文档、DDL、迁移或代码结构证据不足 |
| `配置证据缺失` | 任务依赖实际配置，但快照、键、绑定或生效条件证据不足 |
| `基线漂移` | 相关代码晚于 Git 基线，或点名变更包尚未进入 `processed_packages` |
| `来源冲突` | 任意两类来源对同一事实给出不兼容结论 |
| `待确认` | 候选无法唯一映射或证据不足但尚不构成明确缺失 |

不要把当前提交晚于基线自动等同于所有实体漂移，也不要把 DDL 缺失自动等同于阻断。

## 就绪判断

- `就绪`：实体唯一，四条路径已检查，表与配置关系明确，画像必需字段齐全。
- `有条件就绪`：缺失项不改变方向，已给出明确假设和补证方式。
- `阻断`：范围未授权、实体无法确定、关键冲突会改变方向，或任务依赖的实际配置因目录、指纹或快照失效而无法验证。
