# KnowledgeBase 任务上下文

## 概述

从用户当前任务出发，沿知识库语义、当前代码、数据模型、配置四条独立证据路径渐进读取，生成支持下游工作的最小任务上下文包。本 Skill 只接受 Manifest 4.0，是需求、Design、Plan、Coding、Testing、Review 或 Debug 的前置上下文阶段，不代替下游工作，也不调用或依赖 `cadence-workflow`。

上下文准备完成后，调用方必须继续用户原始任务；只有用户明确只要求加载、整理或保存上下文时，才在上下文包处结束。

## 手动入口

- Claude Code 插件：`/cadence-init:knowledge-base-context`
- Codex：`$knowledge-base-context`

自动触发只由 Frontmatter `description` 决定。Manifest 在触发后提供 Schema、授权范围和证据基线，不参与 Skill 发现。

## 必读资源

- 执行渐进读取前读取 `references/progressive-retrieval-guide.md`。
- 识别主辅画像后读取 `references/task-profiles.md` 中对应画像。
- 需要核对完整输出形状时读取 `references/demo.md`。
- 只有用户明确要求保存任务上下文时，使用 `assets/task-context-template.md`。

## 强制边界

- 四条路径同等重要，必须分别记录来源、缺口和停止原因，不得把数据模型或配置并入“当前代码”。
- 每次任务都检查与逻辑表、数据源、配置组和配置键的直接关系。确认无直接关系后记录结论并停止该方向，不扫描全部数据模型或配置包。
- 只在 Manifest 4.0 的工程、数据模型和配置授权范围内读取；不得重新解释用户输入或自行扩大范围。
- 外部配置快照目录全程只读；不连接配置中心、数据库、中间件或远程环境，不执行部署、发布、启动或迁移脚本。
- 默认只把上下文返回当前会话，不创建任务文件。
- 不修改业务代码、KnowledgeBase、Manifest、变更包或下游交付物。
- 不复制完整源码、整篇知识库文档或配置快照，只保留摘要、稳定 ID、精确位置和必要短片段。
- 工作区未提交修改属于当前代码证据，不清理、不覆盖、不恢复。
- 敏感配置只返回配置键、用途、状态和绑定位置；值统一写为 `<redacted>`。

## 工作流程

### 0. Schema 4.0 前置校验

1. 读取当前项目适用的 `AGENTS.md`、`CLAUDE.md` 和项目规则。
2. 定位 `cadence/knowledge-base/manifest.yaml`，只接受 `schema_version: "4.0"`。
3. 必读以下 Manifest 4.0 信息：
   - `scope.projects`、`scope.data_models`、`scope.configurations`。
   - `evidence.data_model_sources` 中的 DDL、迁移、Entity、Mapper、SQL 和人工资料状态。
   - `evidence.configuration_snapshots.baseline` 的快照标识、环境、外部目录、授权指纹和来源元数据。
   - `update.last_change_package` 与 `update.processed_packages`。
   - `git.repositories` 中的分支、`baseline_commit` 和仓库范围。
4. 获取当前分支、提交和工作区状态，只用于识别任务相关基线漂移。

Manifest 缺失、Schema 不是 4.0 或缺少任务所需授权范围时立即停止，报告缺失路径或版本，并引导执行 `knowledge-base-bootstrap`。不得兼容其他 Schema、自动迁移或回退为普通全仓分析。

### 1. 识别任务画像与种子

固定画像只有七类：需求澄清、Design、Plan、Coding、Testing、Review、Debug。选择一个主画像，可附加最多两个辅助画像。

从用户请求提取业务词，以及已知页面、API、服务、逻辑表、字段、数据源、配置组、配置键、文件、符号、错误信息、目标环境、MR 和变更包。用户明确点名对象优先于模糊业务词。

### 2. 建立四类渐进证据路径

按固定顺序分别建立种子，不得合并列：

```text
知识库语义：README → 领域索引 → 稳定 ID → 关系矩阵
当前代码：任务对象 → 文件/符号 → 调用链 → 测试
数据模型：TABLE → 字段级模型 → Mapper/SQL/Entity → DDL/迁移
配置：服务/配置组 → 配置键 → 当前快照文件 → 绑定代码 → 生效条件
```

知识库语义回答“系统如何定义”；当前代码回答“当前提交如何运行”；数据模型回答“字段、约束、SQL 与结构来源是什么”；配置回答“哪个环境的键如何加载、绑定并生效”。

### 3. 检查表和配置关系

每次任务都执行以下检查：

1. 从任务对象沿直接关系定位 `TABLE`、数据源、配置组或配置键。
2. 页面任务先沿 `PAGE → API → SERVICE/MODULE`，再检查该服务的表和配置关系。
3. 已发现直接关系时，只读取相关逻辑表字段文档、相关结构来源、服务配置文档、当前快照文件和绑定代码。
4. 未发现直接关系时，分别记录“无直接表关系”或“无直接配置关系”，并停止对应方向；不得扫描全部 `data-models/`、`configurations/` 或外部快照目录。

默认只扩展一跳。画像必需字段仍缺关键证据时才沿对应关系再扩一跳；公共工具、通用异常、日志和框架基础设施不无限传播。

### 4. 校验基线与变更包

- 对任务相关文件和符号比较 Manifest Git 基线与当前提交；只有相关对象发生变化才标记 `基线漂移`。
- 读取 `update.last_change_package` 和 `update.processed_packages`，判断最近已处理变更包是否影响任务对象。
- 只有相关时才读取最近处理变更包的五份强制文档；无直接关系时记录后停止，不遍历全部 `CHANGE-*` 目录。
- 用户点名一份未登记在 `processed_packages` 的变更包时，读取该包的五份强制文档用于上下文，标记 `基线漂移`，并明确该包尚未纳入 KnowledgeBase 基线；本 Skill 不处理或登记该包。

### 5. 画像定向深化

按 `references/task-profiles.md` 补齐主画像和辅助画像的专属上下文。Review 必须对照 MR、数据库文档、配置文档和变更包声明；Debug 必须检查配置快照与生效条件、数据源路由、SQL 和字段状态。

某一方向足以支持下游判断时立即停止该方向读取。

### 6. 四类证据对照

每项关键结论分别记录 KnowledgeBase、当前代码、DDL/数据模型和配置快照证据。状态只使用：

- `一致`
- `KnowledgeBase 缺失`
- `源码缺失`
- `数据模型证据缺失`
- `配置证据缺失`
- `基线漂移`
- `来源冲突`
- `待确认`

当前行为以当前提交中的可验证代码描述；业务语义保留 KnowledgeBase 和用户资料定义；结构事实按可定位的数据模型来源描述；实际配置按授权快照、绑定和生效条件描述。来源不一致时保留各侧结论和任务影响，不静默覆盖。

### 7. 停止并输出

同时满足以下条件后停止读取：

- 任务边界、主画像和目标实体已确定。
- 四条路径均已取得直接证据，或已记录无直接关系、缺失或阻断原因。
- 表、数据源、配置组和配置键的任务关系已检查。
- 主辅画像必需字段已有可定位证据。
- 相关 Git 基线和变更包状态已核对。
- 关键冲突、漂移和缺口已显式记录。
- 继续扩展只会进入公共基础设施、无关表或无关配置。

停止读取只表示上下文收集完成。输出上下文包后，将控制权交回当前代理继续原始任务。

## 异常处理

| 情况 | 处理 |
|------|------|
| Manifest 缺失或不是 Schema 4.0 | 立即停止；不得回退全仓分析 |
| 数据模型范围为 `不适用` | 记录“无直接表关系”或授权不适用，停止数据模型方向 |
| DDL 缺失 | 使用字段级表文档、迁移、Mapper、SQL、Entity 和人工资料继续；不能确认的属性标记 `数据模型证据缺失` 或 `待确认` |
| 相关表没有任何结构证据 | 标记 `数据模型证据缺失`；若会改变任务方向则阻断 |
| 配置范围为 `不适用` | 记录“无直接配置关系”或授权不适用，停止配置方向 |
| 配置授权指纹缺失、失配或目录变化 | 任务依赖实际配置时阻断；不得读取配置内容或输出实际配置结论 |
| 配置外部目录不存在、不可读或越界 | 任务依赖实际配置时阻断；不连接远程配置源补取 |
| 只发现配置键，未发现绑定或生效条件 | 标记 `配置证据缺失` 或 `待确认`，不得断言配置已生效 |
| 用户点名未处理变更包 | 读取该包，标记 `基线漂移`，说明尚未纳入 KnowledgeBase；不修改 Manifest |
| 页面任务 | 沿 `PAGE → API → SERVICE/MODULE` 后检查相关表与配置，不直接扫描全部后端 |
| 同名实体无法唯一匹配 | 列出候选并询问，不按名称猜测 |
| 来源冲突会改变任务方向 | 保留四类证据并询问用户 |
| 请求超出 Manifest 范围 | 停止越界读取，说明需要新的用户授权范围 |
| 敏感配置 | 只记录键、用途、状态、绑定位置，值写为 `<redacted>` |

需要结构化提问时，Claude Code 使用 `AskUserQuestion`；Codex 工具可用时使用 `request_user_input`；工具不可用时使用普通文本提问。范围和实体明确时不得重复确认。

## 工具策略

- 大范围关系和影响面优先使用可用 CodeGraph。
- 精确类、方法、路由和配置绑定结构优先使用 `ast-grep outline`。
- 已知稳定 ID、路径、表名、字段、配置键和变更包使用 `rg` 与定向读取。
- 结构化工具不可用时降级为文本检索，但不得扩大为无边界扫描。

## 输出契约

输出固定包含十三节：

1. 任务识别
2. 任务理解
3. 核心实体
4. 四类证据矩阵
5. 关系与影响面
6. 数据模型上下文
7. 配置上下文
8. 相关变更包
9. 画像专属上下文
10. 约束与现有模式
11. 冲突、缺口与待确认项
12. 下游使用建议
13. 就绪状态

就绪状态只使用：

- `就绪`：关键上下文完整，没有影响方向的未决冲突。
- `有条件就绪`：存在非阻断缺口，可以在明确假设下继续。
- `阻断`：目标无法确定、关键规则缺失、任务依赖的实际配置不可验证，或冲突会改变任务方向。

用户明确要求复用、交接或审计时，按模板保存到：

```text
cadence/knowledge-base/task-contexts/
YYYY-MM-DD_任务上下文_任务名称_v1.0.md
```

任务快照记录 Manifest 基线和当前提交，但不加入 Manifest，也不反向更新领域知识库。

## 完成条件

- 已识别一个主画像和不超过两个辅助画像。
- 四条路径均已实际检查并分别记录证据或停止原因。
- 每次任务都已检查表和配置关系，没有因无直接关系扩大扫描。
- Manifest 的数据模型来源、配置授权快照、最近处理变更包和 Git 基线已读取。
- 所有关键结论具有稳定 ID、精确文件、符号、字段、配置键或变更包位置。
- Review 或 Debug 的强制核对项已完成。
- 冲突、漂移、缺口和就绪状态明确。
- 已将上下文交回调用方继续原始任务，或用户明确只要求上下文。
- 本 Skill 未绑定、调用或修改 `cadence-workflow`。
