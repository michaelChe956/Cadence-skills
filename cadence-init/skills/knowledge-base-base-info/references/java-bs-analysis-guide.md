## 仓库与模块信号

| 信号 | 可能含义 | 需要继续确认 |
|------|----------|--------------|
| 根 `pom.xml` 含 `<modules>` | Maven 多模块 | 子模块是否独立服务 |
| 多个启动类 | 多服务或测试入口 | 是否在生产构建中启用 |
| `settings.gradle` | Gradle 多项目 | include 与目录映射 |
| 多个 `package.json` | 多前端或 Monorepo | workspace 和部署单元 |
| Gateway 配置 | 可能存在外部路由 | 实际 Profile 与部署配置 |

## Java 分析重点

- `@SpringBootApplication` 的扫描范围
- `@EnableConfigurationProperties`

- MyBatis-Plus Wrapper 和逻辑删除

### 隐式调用

- AOP 切面

- 反射、SPI、动态代理
- Spring Bean 名称查找

## 前端分析重点

- 锁文件用于确认实际依赖版本
- 构建配置用于确认别名、代理和环境变量

- 请求封装可能统一注入 Token、租户和错误处理
- 状态管理可能控制权限、Feature Flag 和动态路由

## DDL 分析重点

按数据库方言识别：

- 标识符大小写与引用方式
- 自增、序列或触发器生成 ID
- 索引类型、分区和表空间
- 字段注释与表注释
- 视图、函数、过程和触发器依赖

跨文件 DDL 必须先确定执行顺序和所属 Schema。分库分表需要区分逻辑表与物理表，不重复把每个物理分片当成独立业务实体。

## 字段级数据模型生成规则

### 固定输出层级

`data-models/` 始终生成，固定分为三层：

1. `data-models/README.md`：数据模型总索引，覆盖全部数据库、Schema 和逻辑表。
2. `data-models/<数据库或 Schema 稳定 ID>/README.md`：当前数据库或 Schema 的表清单与关系导航，不复制完整字段清单。
3. `data-models/<数据库或 Schema 稳定 ID>/<逻辑表稳定 ID>.md`：每张逻辑表的字段级文档。

禁止用单个 `data-model-overview.md` 替代上述输出。一张逻辑表只生成一个文档；`t_order_00` 至 `t_order_15` 等物理分片只写入逻辑表文档的分库分表章节。

### 逻辑表识别

- 优先使用 DDL 或迁移中的表定义确认物理名称，以配置中的路由规则识别逻辑表与物理分片范围。
- Entity 的 `@Table`、MyBatis Mapper、SQL 的 `FROM`、`JOIN`、`INSERT INTO`、`UPDATE` 和 `DELETE FROM` 可以提供代码映射证据。
- 多个物理表具有相同结构并符合明确分片规则时，合并为一个逻辑表；不能仅凭名称相似自行归并。
- 为逻辑表分配稳定 ID，例如 `TABLE-order`；数据库、Schema、服务、API、页面和配置组也使用稳定 ID 关联。

### 字段清单

每张逻辑表必须逐字段记录：字段、类型、可空、默认值、主键、含义、代码映射、证据状态和证据位置。字段清单的证据状态只允许：

- `DDL 已确认`
- `迁移已确认`
- `代码可推导`
- `用户提供`
- `来源冲突`
- `待确认`

证据状态描述当前字段行最可靠的结构来源。某个属性缺少证据时，该属性单元格仍写 `待确认`，不能因字段名可由代码推导而补造类型、可空性、默认值或主键状态。证据位置必须定位到文件、对象、SQL statement 或用户资料条目。

### 索引、约束与关系

- 只有 DDL、迁移或明确人工资料直接定义的实际索引、主外键、唯一约束和检查约束，才能按对应证据状态记录为数据库结构。
- Entity 注解、MyBatis 映射或 SQL 用法只能描述代码侧意图或候选关系；没有 DDL 时，实际数据库索引、默认值和约束写 `待确认`。
- 同名字段不能单独证明外键关系。显式外键可标 `DDL 已确认` 或 `迁移已确认`；明确 ORM 关联、SQL `JOIN` 语义或用户资料只能按其来源记录，并说明未确认数据库外键。
- 记录复合索引或复合约束时保留字段顺序；来源未给出顺序时不得补全。

### Mapper、SQL 与读写服务

- 记录 Entity 字段与数据库字段映射、Mapper 接口、Mapper XML statement、Repository 查询、JDBC Template 和手写 SQL。
- 按 `SELECT`、`INSERT`、`UPDATE`、`DELETE` 区分操作，并关联调用它们的服务稳定 ID 与方法位置。
- 能追踪到 API 或页面时，分别关联 API 稳定 ID 和页面稳定 ID；无法追踪时写 `待确认`，不得仅凭命名猜测。
- 动态 SQL 需要记录条件分支可能引用的字段，并说明静态分析无法保证运行时覆盖完整。

## 证据合并与降级

### 离线证据边界

数据库事实只能来自 Manifest 授权的只读 DDL、迁移、代码、配置和人工资料。不得建立 JDBC、数据库客户端或其他数据库连接，不得查询系统表、`information_schema`、Schema Catalog 或数据库结构，也不得访问在线元数据服务补充或验证证据。授权资料没有覆盖的结构属性必须标记 `待确认`，不能通过连接运行中数据库补证。

### 来源处理顺序

不要用固定优先级覆盖冲突。先分别记录 DDL、迁移、Entity、Mapper、SQL、配置和人工资料，再按属性合并：

1. 来源一致时保留全部证据位置，并使用最直接的证据状态。
2. 名称、类型、可空性、默认值、主键或约束不一致时标 `来源冲突`，列出各来源原值及影响。
3. 迁移片段只有在所属 Schema、执行顺序和适用版本可确认时标 `迁移已确认`；否则说明限制并标 `待确认` 或 `来源冲突`。
4. 用户资料明确给出的事实标 `用户提供`，不自动升级为 DDL 或迁移事实。

### 无 DDL 场景

没有 DDL 时仍生成总索引、Schema 索引和每张逻辑表的字段级文档：

- Entity、Mapper 和 SQL 明确出现的表名、字段名和映射关系可标 `代码可推导`。
- Java 类型只能记录为代码类型；数据库类型若无迁移或人工资料支持则写 `待确认`。
- 实际可空性、默认值、主键、外键、唯一约束、检查约束和索引全部保持 `待确认`。
- 在表文档的“证据与来源冲突”中声明完整性限制，例如动态 SQL 分支、运行时表名、未纳入的外部 Mapper 或缺失迁移顺序。
- 无任何来源支持的字段或属性不得补造；未覆盖对象进入 Schema 索引和 `open-questions.md`。

## 配置与中间件

配置值的存在不等于生效。结合以下证据判断：

1. Profile 或配置中心加载范围
2. Bean 条件装配
3. 调用、Listener、Producer 或客户端创建
4. 网关、部署或运行资料

## 横切关注点

重点寻找：

- Spring Security Chain、权限注解和自定义鉴权
- `@Transactional`、事务管理器和事件边界
- `@Cacheable`、RedisTemplate 和本地缓存
- Resilience4j、Sentinel、Hystrix 或自定义重试
- 全局异常处理和错误码枚举
- 日志 Trace ID、Micrometer、OpenTelemetry 或 SkyWalking

## 常见误判

- 依赖存在即认定实际使用
- Controller 存在即认定外部暴露
- 同名字段即认定外键关系
- 开发配置即认定生产配置
- 测试启动类即认定生产服务
- Entity 结构即认定数据库实际结构
- 代码查询字段即认定真实索引、默认值或数据库约束
- 同名字段即认定数据库外键
- 为每个物理分片重复生成逻辑表文档
- 用数据模型摘要代替每张逻辑表的字段清单
- README 中的旧版本说明即认定当前版本
