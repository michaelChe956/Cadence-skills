# Design

## Context

kb-eval 已有 `kb-eval-pipeline` 契约（5 条 requirement：fixture 资产与埋点契约、三层断言器与自测、阶段化流水线与断点续跑、车道分层与触发、调优回路与断言红线），但没有一条约束「无 KB 臂的可信性」与「跨运行可比性」——而这两点正是配对实验结论的全部依据。

实现侧已完成修复（见 proposal），本变更只做契约化。

## Goals / Non-Goals

**Goals:**

- 把「KB 产物与判据不得进入容器」固化为可验收要求，且表述为**排除清单**机制，使新增产物必须同步登记。
- 把「fixture hash 确定性」与「KB 以入库快照提供」固化为可验收要求。

**Non-Goals:**

- 不改变容器网络隔离、进程沙箱或 agent 权限模型（本机制只针对 harness 自身产物的可见性）。
- 不规定快照的存储格式与目录命名（PROVENANCE.md 作为操作层约定，不进契约）。
- 不为「补齐历史快照的 baseline 差异」设要求——重建时机属操作决策，已记录在溯源文件。

## Decisions

- **用「排除清单」而非「单一路径」表述**：泄漏面会随产物增加而扩大（results → kb-archive → 未来可能还有别的），单路径写法正是本轮踩到的坑。写成清单后，新增同类产物时契约天然要求同步登记。
- **两处入口都写进 requirement**：只堵 `-v` 挂载不够——overlay 会把内容解包到 skills 目录，agent 从工作目录同样可读。实测确认两条路径互不覆盖。
- **确定性用「提交时间固定」而非「记录并用非确定性 hash」**：后者让知识库的 `baseline_commit` 永远只是历史快照值，agent 每次都要核对漂移；前者一次性消除。
- **快照 requirement 只要求「入库 + 溯源 + 重建时一致」，不要求「现存快照的 baseline 已一致」**：现存快照构建于确定性修复之前，其差异已由溯源文件如实记录、重建时机已知；把「现存即一致」写成 MUST 会与事实不符。

## Risks / Trade-offs

- 风险：排除清单是黑名单，新增产物若忘记登记仍会泄漏。缓解：requirement 明确「新增同类产物 MUST 同步加入清单」，且断言层可在 Tier-0 增加清单覆盖检查（后续项，不在本变更）。
- 权衡：快照入库使仓库多出一份 KB 产物（66 文件 / 568 KB）。换来的是新克隆即可跑有 KB 臂、且跨运行的 KB 内容受控（唯一变量成立）。
