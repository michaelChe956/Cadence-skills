## Context

五类产物缺失共享同一机制级根因：模板（assets/references）完整，但各 Skill 完成条件与 global-validation 清单未把模板关键产物列为强制验收项。本设计在不改动任何 assets 模板与 demo 的前提下，把强制力落在三层：产生层（各领域 Skill 完成条件与工作流程）、交接层（pages→api 候选清单契约）、验收层（global-validation 内容完整性维度）。

## Goals / Non-Goals

**Goals**

- 让五类已知缺口在下次执行时必然被拦下：产生层失败关闭，或 global-validation 判 `failed`。
- 所有新增完成条件必须可机械判定（每条能客观回答"是/否"）。
- 只改 Markdown 文档，不新增代码。

**Non-Goals**

- 不修复已生成的业务项目 KnowledgeBase 产物（含 `/tmp/knowledge-base-3`）。
- 不修改 assets 模板、demo 文件、`knowledge-base-overview`、`knowledge-base-update`。
- 不引入独立校验脚本或 lint 工具（目标为多客户端环境，脚本未必可执行，且无法覆盖语义符合性）。

## Decisions

### 决策 1：强制力采用三层强化，而非单点集中验收

- 产生层：各 Skill 完成条件补硬验收，错误在产生时即失败关闭。
- 交接层：pages 与 api 之间建立写死的候选清单契约。
- 验收层：global-validation 增加内容完整性维度作为兜底。
- 备选方案"只强化 global-validation"被否决：错误发现最晚、返工成本最高，且分批/越序执行时单点验收来不及介入（真实执行日志中已发生越序）。
- 备选方案"独立校验脚本"被否决：违反仓库"非必要不编写代码"规则，多客户端环境脚本未必可执行，且无法覆盖语义符合性。

### 决策 2：对内 REST 文档的生成责任归 api，pages 只负责发现与登记

- pages 深挖页面时把未登记 REST 按契约格式登记为 `API-CANDIDATE-*`；api 新增"页面链路模式"消费清单、按 `demo_对内REST` 模板生成正式文档并升级稳定 ID。
- 备选方案"pages 自给自足生成接口文档"被否决：接口文档出现两个写入方，模板演进易分叉，且与"页面必须链接 interfaces/ 主文件"的现有规则矛盾。
- 备选方案"api 先全量盘点、pages 后匹配"被否决：违背用户按路由点名的意图，全量扫描成本高、噪声大。

### 决策 3：pages 指定模式按对象粒度分流

- Manifest `scope.pages.selected` 条目区分"应用级"与"路由/菜单级"两种粒度。
- 应用级：保留现有概览路径。
- 路由/菜单级：必须逐路由深挖——菜单→路由定位（记录证据，无法唯一匹配时列候选并询问）→ 每条路由生成 `PAGE-*`/`ROUTE-*` 单页面文档（含模板第 3 节与 4.1~4.5 节）→ 页面全部请求逐条追踪到 Method+标准 Path → 已登记匹配稳定 API ID，未登记生成候选。只产出应用级概览视为未完成。

### 决策 4：pages 对 interfaces 索引的写入授权最小化

- pages 唯一获准写 `interfaces/` 的位置是 `interfaces/README.md` 的"对内能力"分区候选表；条目固定七字段：候选 ID、HTTP Method、标准 Path（合并 baseURL/代理/网关重写）、前端应用、调用位置（文件+行号）、请求封装链、来源 PAGE/ROUTE ID。
- 该授权与格式在 api 与 pages 两个 SKILL 中逐字段一致地写明，避免交接失真。

### 决策 5：配置完整性以"键数核对"为机械判定手段

- 每个服务配置文档遵循 10 节模板；第 4 节配置键清单逐键完整，清单行数 = 来源文件实际键数（按既有去重与合并口径，相同内容文件合并时按全集计）。
- 元数据必须同时记录`来源文件键数`与`文档收录键数`，供 global-validation 机械比对。
- 脱敏边界澄清：脱敏对象是值不是键——键名、用途、值类型、敏感级别必须逐键列出，仅值写 `<redacted>`；禁止以敏感为由整条省略键。

### 决策 6：context 的强制化采用"逐层门禁 + 输出门禁 + 准确性自查"三段式

- 逐层门禁：四条证据路径每层必须输出本层证据摘要（来源/精确位置/本层结论/停止原因）才允许进入下一层；"默认一跳、扩跳必须记录理由"从 references 上提为正文强制；四条路径各自必须有证据或停止原因，禁止留白。
- 输出门禁：十三节输出契约逐节必填（无内容节写明`无直接关系/证据缺失+原因`）；每个关键结论必须挂稳定 ID + 精确文件/行号或显式状态枚举；就绪状态三级判定给出必须判`阻断`的条件清单。
- 准确性自查（输出前四步，留痕）：稳定 ID 解析复核（读文件确认存在）、Method+Path/表名/字段名/配置键逐字一致复核、候选无法唯一匹配时强制列清单、证据矩阵每行结论必须有状态。

### 决策 7：global-validation 新增四项内容完整性检查，任一不过判 failed

| # | 检查 | 机械判定方式 |
|---|------|--------------|
| 1 | API 配套文件存在性与索引双分区（API 领域适用时） | 每个请求响应能力主文件存在配套 `_参数与报文.md`；索引同时含对外/对内分区（允许"未盘点+原因"，不允许整块缺失） |
| 2 | 配置键数一致性（配置全量/指定时） | 每个服务配置文档元数据：`来源文件键数` == `文档收录键数` |
| 3 | PAGE 级实体存在性（Pages 适用且含路由/菜单级条目时） | 每条点名路由存在 `PAGE-*`+`ROUTE-*` 实体与单页面文档；页面文档 API 引用不得为零链接 |
| 4 | 模板节结构符合性 | 在现有占位符检查外增加节序比对：接口主文件 11 节、参数报文 5 节、配置文档 10 节、页面文档含第 3/4 节；自创节结构判 failed |

失败处理沿用现有规则：写 `global_validation: failed`、保持 `in_progress` 与空 `completed_at`、只报告缺失项，不删除产物。

## 验证策略

范围不含产物修复，采用三重验证：

1. **回溯验收测试（核心证据）**：用决策 7 的新版清单逐条对 `/tmp/knowledge-base-3` 旧产物执行验收，预期 `failed` 且报告命中全部已知缺口（缺 4 个配套参数报文、`CONF-bss` 键数 587≠27、0 个 PAGE 实体、对内分区缺失、4 个接口主文件非 11 节）。任一已知缺口漏报，说明清单仍未覆盖，继续修订。
2. **可判定性审查**：新增完成条件逐条通读，清除歧义措辞，每条可机械回答"是/否"。
3. **契约一致性检查**：api 与 pages 两侧候选清单七字段逐字段比对一致；pages 对 interfaces 索引的写入授权在两边表述一致。

## Risks / Trade-offs

- 首次执行耗时与产物体量上升：有意为之的成本转移，把事后发现内容丢失的代价前移为当次执行做完整。
- 完成条件与验收条目增多带来 SKILL.md 篇幅增长：通过只新增可机械判定条目、不复制模板正文来控制膨胀。
- 旧产物在新验收下会判 failed：符合预期，这正是回溯验收测试要证明的行为；不因此对旧格式做兼容豁免。
