# Design

## 1. 边界

本变更新增的是 **KnowledgeBase 输入侧** 的能力，位于 `knowledge-base-bootstrap` 之前：

```text
用户 → knowledge-base-user-input（生成 9 文件草稿 + 确认清单）
        → 用户确认/修订
          → knowledge-base-bootstrap（校验输入 → 初始化 Schema 4.0）
```

它不改变 `knowledge-base-bootstrap` 的输入契约、状态枚举、生命周期判定、固定产物检测集合与阶段顺序，也不改变任何领域 Skill 的行为。

## 2. 关键决策

### D1 产物只落在 `user-input/`

bootstrap 的生命周期判定把 `manifest.yaml`、`input-inventory.md`、`README.md`、`base-information.md`、`development-guide.md`、`interfaces/`、`pages/`、`services/`、`data-models/`、`configurations/`、`evidence/`、`business/`、`capabilities/`、`domain-glossary.md`、`open-questions.md`、`change-history.md` 作为固定产物检测集合。只要其中任意一个先于 Manifest 存在，bootstrap 就走“Manifest 缺失 → 立即停止”分支。

因此草稿生成 MUST NOT 触碰 `cadence/knowledge-base/` 下 `user-input/` 以外的任何路径。确认清单也因此不落盘（见 D8）。

### D2 模板单一来源

9 个文件的章节、表格列头与字段顺序 MUST 以 `cadence-init/skills/knowledge-base-bootstrap/user-input/` 的模板为准，本 Skill 不复制模板副本，避免两处模板漂移。生成时删除面向填写者的指导语与示例行，保留结构骨架。

### D3 状态值严格三态，待确认信息只写自由文本

bootstrap 的输入校验要求状态逐字取 `全量`/`指定`/`不适用`。草稿若在状态值里混入 `全量【待确认】`，会直接触发 bootstrap 的“未知状态 = 输入缺失”停止。

因此草稿 MUST 把「已确认事实」与「需用户裁决」分离：

- 状态字段：只能是三个合法值之一，不带任何后缀标记。
- 自由文本字段（备注、不适用原因、分析说明、状态列、说明段落）：承载 `【待确认】` 标记、证据位置与问题描述。

### D4 不适用领域的文件取舍

契约规定领域为 `不适用` 时不要求引用文件可用。因此：

- 判为不适用但探测到该领域证据（典型：配置目录存在但不是不可变快照）→ 仍生成对应 scope 文件作为证据记录，`base-info.md` 保留资料链接，状态写 `不适用` + 具体原因。
- 完全无证据（典型：无前端工程、无中间件依赖）→ 不生成该 scope 文件，并在 `base-info.md` 删除该领域的资料链接，避免留下失效链接。

### D5 配置默认 `不适用`

契约要求配置来源必须是锁定发布批次的不可变快照（提交、标签或导出快照），持续变化的工作目录不合格。目标项目的本地配置目录天然不满足该条件，若草稿把配置写成 `全量`，bootstrap 必然在快照可读性与锁定依据门禁处停止。

草稿默认把配置判为 `不适用`，原因写明“本地工作目录不是不可变快照”，同时在 `configuration-scope.md` 记录探测到的配置目录、纳入文件数量与文件规则摘要，供用户指定锁定批次后改为 `全量` 或 `指定`。

### D6 DDL 不伪造

`database-ddl.sql` 是可选证据。只在找到单一权威 DDL 文件（`schema.sql`、`init.sql`、`db/**/*.sql` 等）时复制其内容，并做敏感信息检查；找不到时仍生成该文件，但只写一段说明“无权威 DDL，结构证据见 data-model-scope.md”，不编造表结构。

### D7 对外能力清单列全、状态留待确认

契约规定“工程内发现但未登记的能力归入对内能力”。草稿若只列自认为对外的能力，其余入口会被静默归入对内，用户的对外清单就此失真。

因此草稿 MUST 列出探测到的全部入口（REST、RPC、消息生产/消费、文件、定时任务），能力类型逐个标注，`状态` 列写 `待确认`，并在文件内提示用户逐项裁决对外属性。

### D8 确认清单只进会话

`user-input/` 只允许 9 个输入文件；额外落盘文件会污染 bootstrap 的输入清单解析。因此确认清单以会话输出形式交付，包含逐文件的结论、证据位置、待确认项与建议动作。

### D9 不自动调用 bootstrap

草稿落盘后 MUST NOT 自动触发 `knowledge-base-bootstrap`。用户确认是草稿转为用户权威输入的前置条件。

## 3. 证据采集方式

沿用仓库既有的代码阅读规则：大范围关系用 CodeGraph，精确结构用 `ast-grep outline`，工具不可用时退化为有边界的文本检索与定向阅读。

选择 LLM 只读扫描而非确定性脚本：Java 与 Vue/React 的工程形态、构建体系与目录约定差异极大，用脚本穷举解析的误判率高、维护成本高；只读扫描 + 强制证据位置（`文件:行号`）能把结论锚定回真实代码，且与既有 KB Skill 家族风格一致。

## 4. 失败处理

| 场景 | 行为 |
| --- | --- |
| 门禁不通过（已有输入、知识库已存在、项目类型不符） | 立即停止，不写任何文件，报告原因与继续入口 |
| 证据不足 | 不推测补写：状态落到安全的 `不适用` 或写 `【待确认】`，并在确认清单中列为待裁决项 |
| 采集过程中断 | 先在内存中完成全部 9 个文件内容再逐个原子写入；中断时报告已写入与缺失文件，不静默留半成品目录 |
| 检测到敏感值 | 立即停止写入该文件，报告位置，值不落盘 |

## 5. 迁移与兼容

无数据迁移。新增 Skill 不改变任何既有契约；`network-skill-install` 规格中“14 个 skill”的数量口径是唯一需要同步的既有断言。
